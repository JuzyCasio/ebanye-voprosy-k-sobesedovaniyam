## Основы асинхронного обмена

### 1. Что такое брокер сообщений

Брокер сообщений — это промежуточный сервис между отправителем и получателем сообщений.

Вместо того чтобы один сервис напрямую вызывал другой, он отправляет сообщение в брокер, а другой сервис забирает его позже.

#### Схема взаимодействия

```text
Сервис заказов  --->  Брокер  --->  Сервис оплаты
Producer              Broker       Consumer
```

#### Зачем нужен брокер

**Брокер помогает**

- **Развязать сервисы.** Producer не обязан знать, кто именно обработает сообщение, а consumer может быть временно недоступен.
- **Сгладить нагрузку.** Если сообщений пришло много, они накапливаются в очереди и обрабатываются постепенно.
- **Повысить отказоустойчивость.** При временном падении получателя сообщения не должны сразу потеряться.
- **Организовать асинхронную обработку.** Заказ можно создать сразу, а письмо, списание бонусов и уведомления выполнить позже.
- **Масштабировать обработку.** К одной очереди можно подключить несколько consumers.

> **Короткий ответ для собеседования**
>
> Брокер сообщений принимает сообщения от одних сервисов, временно хранит их и передаёт другим. Он уменьшает связанность сервисов, помогает переживать пики нагрузки и позволяет выполнять задачи асинхронно.

### 2. Основные термины

#### Message

Message — сообщение, которое передаётся через брокер.

**Обычно содержит**

```json
{
  "event_id": "123",
  "event_type": "order_created",
  "created_at": "2026-07-08T10:00:00Z",
  "payload": {
    "order_id": 777,
    "user_id": 42,
    "amount": 1500
  }
}
```

**В сообщении часто есть**

- id — уникальный идентификатор;
- type — тип события;
- payload — полезная нагрузка;
- timestamp — время создания;
- headers — метаданные;
- correlation_id / trace_id — для трассировки.

#### Producer

Producer — сервис, который отправляет сообщение.

**Пример:**

Order Service создал заказ и отправил событие `order_created`.

#### Consumer

Consumer — сервис, который получает и обрабатывает сообщение.

**Пример:**

Notification Service получил `order_created` и отправил email.

#### Broker

Broker — сервер или кластер, который принимает, хранит и отдаёт сообщения.

**Примеры брокеров:**

- Kafka;
- RabbitMQ;
- NATS;
- Redis Streams;
- ActiveMQ;
- Pulsar;
- SQS.

#### Queue

Queue — очередь сообщений.

Обычно сообщение из очереди получает один consumer.

**Queue**

```text
[message1] [message2] [message3]
```

- Consumer A забрал `message1`;
- Consumer B забрал `message2`.

Очередь часто используется, когда задачу должен обработать один исполнитель.

**Пример:** очередь задач на генерацию PDF.

#### Topic

Topic — логический канал сообщений.

Чаще используется в Kafka/NATS.

**Пример:** topic `orders.created`.

В topic producer публикует сообщения, а consumers читают их.

#### Exchange

В RabbitMQ producer обычно отправляет сообщение не напрямую в очередь, а в exchange.

Exchange решает, в какую очередь отправить сообщение.

**Типы exchange**

| Тип | Как работает |
|---|---|
| direct | отправляет по точному routing key |
| fanout | рассылает во все связанные очереди |
| topic | маршрутизация по шаблону |
| headers | маршрутизация по headers |

#### Пример:

Producer -> Exchange -> Queue -> Consumer
Routing key

Routing key — ключ маршрутизации в RabbitMQ.

**Например**

**orders.created**
orders.paid
orders.cancelled

Exchange может по нему понять, в какую очередь положить сообщение.

**Partition**

В Kafka topic делится на partitions.

**Topic orders**

Partition 0: msg1 msg4 msg7
Partition 1: msg2 msg5 msg8
Partition 2: msg3 msg6 msg9

**Partition нужна для**

параллельной обработки;
масштабирования;
хранения порядка сообщений внутри partition.

#### Важно:

В Kafka порядок гарантируется только внутри одной partition, а не во всём topic.

```sql
Offset

Offset — номер сообщения внутри partition в Kafka.
```

Partition 0:

```sql
offset 0 -> msg A
offset 1 -> msg B
offset 2 -> msg C
```

Consumer хранит offset, чтобы понимать, какие сообщения уже обработал.

**Consumer group**

Consumer group — группа consumers, которые совместно читают topic.

**В Kafka**

Topic orders имеет 3 partition

**Consumer Group: payment-service**

Consumer 1 читает partition 0
Consumer 2 читает partition 1
Consumer 3 читает partition 2

#### Важное правило Kafka:

В рамках одной consumer group одну partition в один момент времени читает только один consumer.

Если consumers больше, чем partitions, лишние consumers будут простаивать.

### 3. Очередь vs Publish/Subscribe

Queue / Point-to-Point

Сообщение обрабатывается одним consumer.

Producer -> Queue -> Consumer 1

```text
                  -> Consumer 2
                  -> Consumer 3
```

Каждое сообщение заберёт только один consumer.

#### Пример:

Очередь задач на обработку изображений

```text
Pub/Sub
```

Одно событие получают несколько независимых подписчиков.

**Order Created Event**

-> Billing Service
-> Notification Service
-> Analytics Service
-> Delivery Service

#### Пример:

Создан заказ.
Один сервис отправляет email.
Второй обновляет аналитику.
Третий резервирует товар.

### 4. Синхронное vs асинхронное взаимодействие

**Синхронное**

Сервис ждёт ответ сразу.

Client -> API -> Payment Service

```text
             <- response
```

#### Плюсы:

проще понимать результат;
проще обрабатывать ошибки;
хорошо для запросов “дай данные сейчас”.

#### Минусы:

сильная связность;
если сервис недоступен, операция падает;
хуже переносит пики нагрузки.
Асинхронное

Сервис отправил сообщение и не ждёт моментальной обработки.

Order Service -> Broker -> Notification Service

#### Плюсы:

- слабая связность;
- лучше отказоустойчивость;
- можно обрабатывать позже;
- хорошо масштабируется.

#### Минусы:

- сложнее тестировать;
- сложнее отлаживать;
- eventual consistency;
- нужны retry, DLQ, idempotency.

### 5. Event-driven architecture

Event-driven architecture — архитектура, где сервисы реагируют на события.

#### Пример события:

**order_created**
payment_completed
user_registered
document_verified

Сервис не говорит другому сервису:

```text
"Отправь письмо"
```

**Он говорит**

```text
"Пользователь зарегистрировался"
```

А другие сервисы сами решают, что делать.

**Command vs Event**

Это частый вопрос на собеседовании.

**Command**

#### Команда — просьба что-то сделать.

**CreateUser**
SendEmail
ReserveProduct

Обычно команда адресована конкретному обработчику.

**Event**

Событие — факт, который уже произошёл.

**UserCreated**
OrderPaid
ProductReserved

Событие не просит ничего сделать, оно просто сообщает о факте.

> **Короткий ответ для собеседования**
>
> Command — это намерение выполнить действие, а Event — это факт, что действие уже произошло. Например, CreateOrder — команда, а OrderCreated — событие.

### 6. Delivery semantics

Это одна из самых важных тем.

Delivery semantics — это гарантии доставки сообщений.

**At most once**

Не более одного раза.

Сообщение может быть потеряно, но не будет обработано дважды.

Producer отправил сообщение.
Consumer получил.
Consumer упал до обработки.
Сообщение потеряно.

#### Плюсы:

быстро;
просто.

#### Минусы:

возможна потеря данных.

Используется там, где потеря не критична:

метрики;
логи;
неважная аналитика.
At least once

#### Как минимум один раз.

Сообщение не должно потеряться, но может быть обработано повторно.

Consumer получил сообщение.
Обработал его.
Но не успел отправить ack.
Брокер отдаёт сообщение снова.

#### Плюсы:

сообщение почти не теряется;
надёжнее.

#### Минусы:

возможны дубли.

Это самый частый вариант в реальных системах.

**Требует**

идемпотентности;
дедупликации;
уникальных message_id/event_id.
Exactly once

Ровно один раз.

В идеале сообщение обрабатывается ровно один раз.

Но на практике это сложная гарантия.

> **Короткий ответ для собеседования**
>
> Exactly once в распределённых системах сложно обеспечить полностью. Обычно брокер может дать определённые гарантии на уровне доставки или записи, но бизнес-обработка всё равно должна быть идемпотентной.

Kafka поддерживает exactly-once semantics для некоторых сценариев, например producer transactions + idempotent producer + корректная обработка offsets. Но на уровне внешней БД или внешнего API всё равно могут быть повторы.

### 7. Ack / Nack

**Ack**

Ack — подтверждение, что сообщение успешно обработано.

**Consumer получил сообщение**
Consumer обработал сообщение
Consumer отправил ack
Broker удалил/пометил сообщение как обработанное
Nack

Nack — отрицательное подтверждение.

**Consumer говорит**

Я не смог обработать сообщение

**После этого брокер может**

- вернуть сообщение в очередь;
- отправить в retry queue;
- отправить в DLQ;
- удалить сообщение.
Auto ack vs Manual ack
Auto ack

Сообщение считается обработанным сразу после получения consumer-ом.

**Минус**

Consumer получил сообщение и сразу упал.
Брокер считает сообщение обработанным.
Сообщение потеряно.
Manual ack

Consumer сам подтверждает успешную обработку.

Это надёжнее.

> **Короткий ответ для собеседования**
>
> Для критичных операций лучше использовать manual ack: сначала обработать сообщение, сохранить результат, а потом подтвердить брокеру успешную обработку.

### 8. Retry

Retry — повторная попытка обработки сообщения.

**Например**

Consumer не смог вызвать внешний API.
Через 10 секунд пробует снова.
Потом через 1 минуту.
Потом через 5 минут.
Какие бывают retry
Immediate retry

Повтор сразу.

#### Плохо, если проблема временная:

Сервис оплаты лежит.
Consumer будет бесконечно долбить его запросами.
Delayed retry

Повтор через задержку.

1-я попытка
через 10 сек
через 1 мин
через 5 мин
Exponential backoff

Задержка растёт постепенно.

1 сек
2 сек
4 сек
8 сек
16 сек

Это снижает нагрузку на проблемный сервис.

#### Что тестировать в retry

**Проверять**

- что сообщение повторяется при временной ошибке;
- что количество попыток ограничено;
- что между попытками есть задержка;
- что после исчерпания попыток сообщение уходит в DLQ;
- что успешная повторная обработка не создаёт дублей.

### 9. DLQ — Dead Letter Queue

DLQ — очередь для сообщений, которые не удалось обработать.

**Туда попадают сообщения, если**

- превышено количество retry;
- сообщение невалидное;
- consumer постоянно падает;
- истёк TTL;
- произошла бизнес-ошибка.

#### Пример:

orders.created -> consumer -> ошибка -> retry -> retry -> retry -> DLQ

**DLQ нужна, чтобы**

- не терять проблемные сообщения;
- не блокировать основную очередь;
- расследовать причины ошибок;
- переобработать сообщения вручную.
Что должно быть в DLQ-сообщении

**Желательно сохранять**

- исходный payload;
- headers;
- причину ошибки;
- количество попыток;
- время первой ошибки;
- время последней ошибки;
- название consumer-а;
- correlation_id / trace_id.

### 10. Poison message

Poison message — сообщение, которое всегда ломает обработчик.

**Например**

```json
{
  "order_id": null,
  "amount": "abc"
}
```

Если его постоянно возвращать в очередь, оно может заблокировать обработку.

#### Решение:

- ограничить retry;
- отправлять в DLQ;
- валидировать схему;
- логировать причину.

### 11. Idempotency

Идемпотентность — возможность безопасно обработать одно и то же сообщение несколько раз без изменения результата после первого успешного выполнения.

#### Пример неидемпотентной обработки:

Получили message payment_completed.
Начислили пользователю 100 бонусов.
Получили дубль.
Начислили ещё 100 бонусов.
Ошибка.

#### Пример идемпотентной обработки:

Проверили event_id.
Если такой event_id уже обработан — пропускаем.
Если нет — начисляем бонусы и сохраняем event_id.
Почему идемпотентность важна

Потому что при at least once delivery дубли возможны почти всегда.

**Причины дублей**

- consumer обработал сообщение, но не отправил ack;
- producer повторно отправил сообщение;
- брокер переотдал сообщение после сбоя;
- произошёл rebalance;
- network timeout;
- retry на стороне producer-а.
Как обеспечить идемпотентность

**Способы**

Уникальный event_id/message_id
хранить обработанные id.
Уникальный бизнес-ключ
например order_id + event_type.
Уникальный constraint в БД
например event_id UNIQUE.
Проверка состояния
если заказ уже PAID, повторно не списывать деньги.
Transactional outbox
событие и изменение бизнес-сущности сохраняются атомарно.

### 12. Ordering — порядок сообщений

Порядок сообщений — сложная тема.

#### Где порядок важен

**Например**

**order_created**
order_paid
order_cancelled

Нельзя обработать order_paid раньше, чем order_created, если логика этого не допускает.

**Kafka**

В Kafka порядок гарантирован только внутри одной partition.

Чтобы события одного заказа шли в правильном порядке, используют один и тот же key:

```python
key = order_id
```

Тогда все события по одному заказу попадут в одну partition.

```python
order_id=777 -> partition 1
```

**RabbitMQ**

В RabbitMQ порядок в очереди может сохраняться, но если у тебя несколько consumers, порядок обработки может нарушиться.

#### Пример:

msg1 забрал Consumer A
msg2 забрал Consumer B

Consumer B обработал быстрее.
msg2 завершился раньше msg1.
Хороший ответ на собеседовании

Если порядок критичен, нужно проектировать это явно: например, в Kafka использовать key, чтобы события одной сущности попадали в одну partition. Также важно помнить, что при параллельной обработке порядок может нарушаться, поэтому consumer должен быть готов к out-of-order событиям или обработка должна быть сериализована для конкретного ключа.

### 13. Eventual consistency

При асинхронной архитектуре данные не всегда становятся согласованными мгновенно.

#### Пример:

Пользователь оплатил заказ.
Payment Service уже знает, что заказ оплачен.
Order Service обновится через событие немного позже.

Это называется eventual consistency.

**То есть**

Система станет согласованной не сразу, а спустя некоторое время.

#### Что это значит для тестирования

В тестах нельзя всегда делать так:

```python
create_order()
pay_order()
assert order.status == "PAID"
```

Потому что статус может обновиться не мгновенно.

**Нужно использовать ожидание**

```python
wait_until(lambda: get_order(order_id)["status"] == "PAID", timeout=10)
```

### 14. Backpressure

Backpressure — ситуация, когда producers отправляют сообщения быстрее, чем consumers успевают их обрабатывать.

#### Пример:

Producer отправляет 10 000 сообщений/сек
Consumer обрабатывает 1 000 сообщений/сек
Очередь растёт

**Последствия**

- растёт lag;
- увеличивается задержка обработки;
- заканчивается память/диск;
- сообщения устаревают;
- сервисы начинают падать.

**Решения**

- добавить consumers;
- увеличить partitions;
- оптимизировать обработку;
- ограничить producer rate;
- использовать batching;
- добавить autoscaling;
- настроить retention/TTL;
- мониторить lag.

### 15. Lag

Lag — отставание consumer-а.

Особенно часто спрашивают в Kafka.

```python
Latest offset = 10000
Consumer offset = 9500
Lag = 500
```

То есть consumer отстаёт на 500 сообщений.

#### Почему растёт lag

**Причины**

- consumer медленно обрабатывает;
- мало consumers;
- мало partitions;
- consumer падает;
- проблемы с БД;
- внешний API тормозит;
- слишком большие сообщения;
- неправильный batching;
- rebalance;
- сеть/диск/CPU.
Что делать, если lag растёт

**Ответ для собеседования**

Я бы сначала посмотрел метрики: consumer lag, скорость поступления сообщений, скорость обработки, ошибки consumer-а, retry, DLQ, CPU/memory, состояние БД и внешних зависимостей. После этого уже решал бы: масштабировать consumers, оптимизировать обработку, увеличить partitions, добавить batching или чинить зависимость, которая тормозит обработку.

### 16. Retention

Retention — сколько брокер хранит сообщения.

В Kafka сообщения не удаляются сразу после чтения consumer-ом.

Они хранятся по настройкам retention:

Хранить 7 дней
или
хранить до 100 GB

**Это позволяет**

- перечитать сообщения;
- восстановить consumer;
- подключить нового consumer-а;
- переобработать данные.
RabbitMQ vs Kafka по хранению

**Условно**

RabbitMQ больше похож на очередь задач;
Kafka больше похожа на распределённый commit log.

В RabbitMQ сообщение обычно исчезает после ack.

В Kafka сообщение остаётся в topic до истечения retention, даже если consumer его прочитал.

## Kafka, RabbitMQ и другие брокеры

### 17. Kafka — главное к собеседованию

Kafka — распределённая платформа для потоковой обработки событий.

#### Основные сущности:

Producer -> Topic -> Partition -> Consumer Group -> Consumer
Kafka topic

Topic — канал сообщений.

#### Пример:

**orders**
payments
users
notifications
Kafka partition

Topic делится на partitions.

**Зачем**

- параллелизм;
- масштабирование;
- распределённое хранение;
- порядок внутри partition.

**Kafka offset**

Offset — позиция сообщения в partition.

Consumer запоминает, до какого offset он дочитал.

**Kafka consumer group**

Consumer group позволяет нескольким consumers читать topic параллельно.

**Правило**

Одна partition в рамках одной group назначается только одному consumer-у.

#### Пример:

Topic orders: 3 partitions

**Consumer group A**
Consumer 1 -> partition 0
Consumer 2 -> partition 1
Consumer 3 -> partition 2

Если добавить четвёртого consumer-а, он будет простаивать, потому что partitions только 3.

**Kafka key**

Key нужен, чтобы управлять попаданием сообщения в partition.

```python
key = order_id
```

Все сообщения с одним key обычно попадают в одну partition.

Это полезно для порядка событий по одной сущности.

**Kafka replication**

Kafka хранит partitions с репликацией.

Partition 0:
leader replica
follower replica
follower replica

Producer и consumer работают с leader replica.

Followers копируют данные.

Если leader падает, Kafka выбирает нового leader из replicas.

**Kafka ISR**

ISR — in-sync replicas.

Это реплики, которые успевают синхронизироваться с leader.

Если replica отстала, она может быть исключена из ISR.

**Kafka acks**

Producer может ждать разные уровни подтверждения.

```python
acks=0
```

Producer не ждёт подтверждения.

Быстро, но ненадёжно.

```python
acks=1
```

Producer ждёт подтверждение от leader.

Если leader подтвердил, producer считает сообщение записанным.

```python
acks=all
```

Producer ждёт подтверждения от всех ISR.

Надёжнее, но медленнее.

**Kafka retries**

Producer может повторять отправку при ошибках.

Но при retry возможны дубли, если не настроить идемпотентность.

**Idempotent producer**

Idempotent producer помогает избежать дублей при повторной отправке producer-ом.

Но это не отменяет необходимость идемпотентной бизнес-логики на стороне consumer-а.

**Kafka rebalance**

Rebalance — перераспределение partitions между consumers.

**Происходит, когда**

- consumer добавился;
- consumer упал;
- изменилось количество partitions;
- consumer слишком долго не отправлял heartbeat.

Во время rebalance обработка может временно останавливаться.

**Kafka commit offset**

Consumer должен фиксировать offset.

**Варианты**

**Auto commit**

Offset коммитится автоматически.

Проще, но есть риск потерь или дублей.

**Manual commit**

Consumer сам решает, когда коммитить offset.

Надёжнее.

**Правильный подход**

1. Получил сообщение
2. Обработал
3. Сохранил результат
4. Закоммитил offset

Если закоммитить offset до обработки, можно потерять сообщение.

### 18. RabbitMQ — главное к собеседованию

RabbitMQ — брокер сообщений, часто используется для очередей задач и маршрутизации.

#### Основные сущности:

Producer -> Exchange -> Queue -> Consumer
Exchange

Producer отправляет сообщение в exchange.

Exchange решает, в какие очереди положить сообщение.

**Queue**

Очередь хранит сообщения до обработки consumer-ом.

**Binding**

Binding связывает exchange и queue.

**Exchange orders**
  binding key orders.created -> Queue created_orders
Routing key

Ключ маршрутизации.

**Например**

**orders.created**
orders.paid
orders.cancelled
Direct exchange

Сообщение попадает в очередь, если routing key совпал точно.

```python
routing key = orders.created
```

**Fanout exchange**

Сообщение рассылается во все очереди, связанные с exchange.

Используется для broadcast.

**Topic exchange**

Маршрутизация по шаблонам.

**Например**

**orders.***
orders.created
orders.#

#### Пример:

orders.*  -> orders.created, orders.paid
orders.#  -> orders.created.eu.spb
Headers exchange

Маршрутизация по headers, а не по routing key.

Используется реже.

**Durable queue**

Durable queue переживает перезапуск RabbitMQ.

**Но важно**

Durable queue сама по себе не гарантирует сохранность сообщения. Сообщение тоже должно быть persistent.

**Persistent message**

Persistent message сохраняется на диск.

Если брокер перезапустится, такое сообщение может быть восстановлено.

**Prefetch**

Prefetch — сколько сообщений RabbitMQ может выдать consumer-у без ack.

**Например**

```python
prefetch = 10
```

Consumer может получить 10 сообщений, но пока не подтвердит их, новые сверх лимита не получит.

**Это помогает**

не перегружать consumer;
равномерно распределять сообщения;
контролировать память.
RabbitMQ ack

Consumer подтверждает обработку через ack.

Если consumer умер без ack, RabbitMQ может вернуть сообщение в очередь.

### 21. Kafka vs RabbitMQ

Очень частый вопрос.

| Критерий | Kafka | RabbitMQ |
|---|---|---|
| Модель | distributed log | message queue |
| Хранение | сообщения хранятся по retention | обычно удаляются после ack |
| Масштабирование | partitions | queues/consumers |
| Порядок | внутри partition | внутри queue, но может нарушаться при параллелизме |
| Replay | удобно перечитывать события | не основной сценарий |
| Use case | event streaming, analytics, event sourcing | task queues, routing, commands |
| Routing | проще, через topics/keys | мощная маршрутизация через exchanges |
| Consumer state | offset | ack состояния очереди |
| Подходит для | больших потоков событий | задач, workflow, RPC-like patterns |

**Как ответить на собеседовании**

Kafka лучше подходит для потоков событий, когда важны высокая пропускная способность, хранение истории, replay и обработка большими объёмами. RabbitMQ чаще используют как классический брокер очередей задач, когда важна гибкая маршрутизация, ack/nack, retry, DLQ и распределение задач между consumers.

### 26. Как тестировать асинхронность в автотестах

#### Главная ошибка — сразу проверять результат.

#### Плохо:

```python
send_message()
assert get_status() == "DONE"
```

Потому что consumer может ещё не успеть обработать сообщение.

**Лучше**

```python
send_message()
wait_until(lambda: get_status() == "DONE", timeout=10)
```

**Пример wait_until на Python**

```python
from collections.abc import Callable
from time import sleep, monotonic
from typing import TypeVar

T = TypeVar("T")

def wait_until(
    condition: Callable[[], T],
    timeout: float = 10.0,
    interval: float = 0.5,
) -> T:
    deadline = monotonic() + timeout
    last_result: T | None = None

    while monotonic() < deadline:
        last_result = condition()
        if last_result:
            return last_result
        sleep(interval)

    raise TimeoutError(f"Condition was not met within {timeout} seconds")
```

**Использование**

```python
result = wait_until(
    lambda: order_client.get_order(order_id)["status"] == "PAID",
    timeout=15,
    interval=1,
)
```

### 29. Schema evolution

Со временем формат сообщений меняется.

**Например, было**

```json
{
  "order_id": 777,
  "amount": 1500
}
```

**Стало**

```json
{
  "order_id": 777,
  "amount": 1500,
  "currency": "RUB"
}
```

**Backward compatibility**

Новая версия consumer-а должна уметь читать старые сообщения.

**Forward compatibility**

Старый consumer должен не падать, если появилось новое поле.

#### Что нельзя делать без осторожности

**Опасные изменения**

- удалить обязательное поле;
- изменить тип поля;
- переименовать поле;
- поменять семантику поля;
- начать отправлять null, если consumer не готов.
Хороший ответ

При изменении схемы сообщений нужно думать о совместимости. Безопасно добавлять необязательные поля. Опасно удалять поля или менять их тип. Для контроля можно использовать schema registry, версионирование сообщений и contract tests.

## Архитектурные паттерны и эксплуатация

### 30. Transactional outbox

Очень важный паттерн.

#### Проблема:

Сервис создал заказ в БД.
Потом должен отправить событие в брокер.
Но между записью в БД и отправкой события сервис упал.

**Получили**

Заказ в БД есть.
События order_created нет.
Другие сервисы не узнают о заказе.
Решение: Outbox

**В одной транзакции сохраняем**

бизнес-данные;
событие в outbox-таблицу.

```sql
BEGIN
  INSERT INTO orders ...
  INSERT INTO outbox_events ...
COMMIT
```

Потом отдельный процесс читает outbox и отправляет события в брокер.

**Пример**
orders table:

```bash
id | status
```

**outbox_events table**
event_id | event_type | payload | status
Зачем это нужно

Outbox помогает не потерять событие между БД и брокером.

> **Короткий ответ для собеседования**
>
> Transactional outbox нужен, чтобы атомарно сохранить изменение бизнес-сущности и событие, которое потом будет отправлено в брокер. Так мы избегаем ситуации, когда данные в БД уже изменились, а событие не было опубликовано из-за падения сервиса.

### 31. Saga pattern

Saga используется для распределённых бизнес-процессов.

**Например заказ**

1. Создать заказ
2. Списать оплату
3. Зарезервировать товар
4. Создать доставку

Если шаг 3 упал, нужно откатить предыдущие шаги.

Но в микросервисах нет одной общей транзакции.

Поэтому используют saga.

**Choreography**

Сервисы реагируют на события друг друга.

OrderCreated -> Payment Service
PaymentCompleted -> Inventory Service
ProductReserved -> Delivery Service

#### Плюсы:

слабая связность.

#### Минусы:

сложнее понять весь процесс;
логика размазана по сервисам.
Orchestration

Есть центральный orchestrator.

**Order Orchestrator**

```sql
  create order
```

**call payment**
  call inventory
  call delivery

#### Плюсы:

проще видеть процесс.

#### Минусы:

orchestrator становится центральной точкой логики.

**Например**

Service A отправляет request message

correlation_id;

### 33. Мониторинг брокеров

#### Что мониторить:

## Собеседование и повторение

### 37. Типовые вопросы на собеседовании

Что такое брокер сообщений?

**Ответ**

Брокер сообщений — это промежуточный сервис для асинхронной передачи сообщений между системами. Producer отправляет сообщение в брокер, а consumer получает и обрабатывает его. Это помогает развязать сервисы, сгладить нагрузку и повысить отказоустойчивость.

#### Зачем использовать брокер, если есть REST API?

**Ответ**

REST удобен для синхронного запроса-ответа, когда результат нужен сразу. Брокер нужен для асинхронной обработки, когда сервисы можно развязать, обработку можно выполнить позже, а сообщения можно буферизовать при пиках нагрузки или временной недоступности consumer-а.

#### Что такое consumer lag?

**Ответ**

Consumer lag — это отставание consumer-а от последних сообщений. Например, если latest offset в partition равен 10000, а consumer обработал только 9500, lag равен 500. Если lag растёт, значит consumer не успевает обрабатывать поток.

#### Что такое DLQ?

**Ответ**

DLQ — Dead Letter Queue. Это очередь для сообщений, которые не удалось обработать после заданного количества попыток или из-за невалидного формата. Она нужна, чтобы не терять проблемные сообщения и не блокировать основную очередь.

Чем Kafka отличается от RabbitMQ?

**Ответ**

Kafka — это распределённый лог событий с хранением сообщений по retention, partitioning и возможностью replay. RabbitMQ — классический message broker с очередями, exchange, routing key, ack/nack и гибкой маршрутизацией. Kafka чаще используют для event streaming и больших потоков событий, RabbitMQ — для очередей задач и маршрутизации сообщений.

Какие гарантии доставки бывают?

**Ответ**

Основные варианты: at most once, at least once и exactly once. At most once допускает потерю сообщений, но не даёт дублей. At least once не теряет сообщение, но возможны дубли. Exactly once сложно обеспечить полностью, поэтому даже при таких гарантиях бизнес-логика consumer-а должна быть идемпотентной.

#### Почему могут появляться дубли сообщений?

**Ответ**

Например, consumer обработал сообщение, но упал до ack или commit offset. Брокер считает сообщение необработанным и отдаёт его снова. Также дубли возможны из-за retry producer-а, сетевых timeout-ов или rebalance в Kafka.

#### Как бороться с дублями?

**Ответ**

Использовать идемпотентную обработку: уникальный event_id, хранение обработанных сообщений, уникальные constraints в БД, проверку текущего бизнес-состояния. Consumer должен уметь безопасно получить одно и то же сообщение повторно.

#### Что такое offset в Kafka?

**Ответ**

Offset — это позиция сообщения внутри partition. Consumer хранит offset, чтобы понимать, какие сообщения он уже прочитал. Offset можно коммитить автоматически или вручную.

#### Что будет, если consumer упал после обработки, но до commit offset?

**Ответ**

После восстановления Kafka может отдать это сообщение повторно, потому что offset не был зафиксирован. Поэтому обработка должна быть идемпотентной.

#### Что будет, если commit offset сделать до обработки?

**Ответ**

Если consumer закоммитил offset, а потом упал до обработки, сообщение может быть потеряно с точки зрения consumer-а. Поэтому безопаснее коммитить offset после успешной обработки.

#### Что такое partition в Kafka?

**Ответ**

Partition — это часть topic-а. Она нужна для параллельной обработки, масштабирования и сохранения порядка сообщений внутри partition. Порядок гарантируется только внутри одной partition.

#### Почему consumers больше, чем partitions, могут простаивать?

**Ответ**

В Kafka внутри одной consumer group одна partition может быть назначена только одному consumer-у. Если consumers больше, чем partitions, части consumers просто нечего читать.

#### Как сохранить порядок сообщений в Kafka?

**Ответ**

Нужно отправлять сообщения с одинаковым key, например order_id. Тогда события одной сущности попадут в одну partition, и Kafka сохранит их порядок внутри этой partition.

#### Что такое prefetch в RabbitMQ?

**Ответ**

Prefetch ограничивает количество сообщений, которые RabbitMQ может выдать consumer-у без подтверждения ack. Это помогает не перегружать consumer и равномернее распределять нагрузку.

#### Что такое durable queue и persistent message?

**Ответ**

Durable queue переживает перезапуск RabbitMQ, а persistent message сохраняется на диск. Для надёжности обычно нужны оба: durable очередь и persistent сообщения.

### 38. Что отвечать QA/SDET про тестирование брокеров

#### Хороший универсальный ответ:

Я бы тестировал брокерную интеграцию на нескольких уровнях. На уровне producer-а проверил бы, что публикуется корректное сообщение в нужный topic/queue с правильным payload, headers, key/routing key. На уровне consumer-а проверил бы обработку валидных, невалидных и дублирующихся сообщений, ack/nack, retry, DLQ и идемпотентность. ### 39. Частые ошибки в тестах с брокерами

Ошибка 1: использовать sleep

#### Плохо:

```python
send_message()
sleep(10)
assert result_exists()
```

**Лучше**

```python
send_message()
wait_until(result_exists, timeout=10)
```

Ошибка 2: не чистить тестовые данные

Если topic/queue общие, один тест может влиять на другой.

**Решения**

- уникальные ids;
- отдельные test topics/queues;
- очистка после теста;
- isolated environment.

Ошибка 3: не проверять дубли

Многие проверяют только happy path.

Но в брокерах дубли — нормальная ситуация.

Если не тестировать DLQ, poison message может сломать очередь в проде.

- обработку consumer-ом.

### 40. Мини-шпаргалка по формулировкам

**Producer**

Producer — сервис, который публикует сообщение в broker.

**Consumer**

Consumer — сервис, который читает и обрабатывает сообщение.

**Topic**

Topic — логический канал сообщений, например orders.created.

**Queue**

Queue — очередь, из которой сообщение обычно обрабатывается одним consumer-ом.

**Partition**

Partition — часть Kafka topic-а для масштабирования и параллельной обработки.

```sql
Offset

Offset — позиция сообщения в Kafka partition.
```

**Consumer group**

Группа consumers, которые совместно читают topic. Внутри group одна partition назначается одному consumer-у.

**Ack**

Подтверждение успешной обработки сообщения.

**Nack**

Сообщение не обработано, его нужно переотправить, ретраить или отправить в DLQ.

**DLQ**

Очередь для сообщений, которые не удалось обработать.

**Retry**

Повторная попытка обработки сообщения.

**Lag**

Отставание consumer-а от последних сообщений.

**Idempotency**

Возможность безопасно обработать одно и то же сообщение несколько раз.

**Retention**

Время или объём хранения сообщений в брокере.

### 41. Практические задачи, которые могут спросить

Задача 1

**Вопрос**

Consumer обработал сообщение, записал результат в БД, но упал до ack. Что будет?

**Ответ**

Брокер может отдать сообщение повторно. Поэтому consumer должен быть идемпотентным. Например, нужно хранить event_id обработанных сообщений или иметь уникальный constraint в БД.

Задача 2

**Вопрос**

В Kafka lag постоянно растёт. Что будешь смотреть?

**Ответ**

**Сначала метрики**

- скорость поступления сообщений;
- скорость обработки;
- consumer lag по partitions;
- ошибки consumer-а;
- retry/DLQ;
- CPU/memory;
- БД и внешние сервисы;
- rebalance;
- сетевые проблемы.

**Потом варианты решения**

- добавить consumers;
- увеличить partitions;
- оптимизировать обработку;
- добавить batching;
- убрать bottleneck в БД/API;
- ограничить producer rate.
Задача 3

**Вопрос**

#### Почему при трёх partitions и пяти consumers два consumers ничего не делают?

**Ответ**

Потому что в Kafka внутри одной consumer group одна partition назначается только одному consumer-у. Если partitions 3, одновременно активно читать могут максимум 3 consumers.

Задача 4

**Вопрос**

#### Как протестировать, что сообщение ушло в DLQ?

**Ответ**

Нужно отправить невалидное сообщение или смоделировать ошибку consumer-а. Проверить, что consumer сделал заданное количество retry, потом сообщение появилось в DLQ с исходным payload и информацией об ошибке.

Задача 5

**Вопрос**

#### Как проверить идемпотентность consumer-а?

**Ответ**

Отправить два одинаковых сообщения с одним event_id. Проверить, что бизнес-операция выполнена один раз: например, одна запись в БД, один платёж, одно уведомление.

Задача 6

**Вопрос**

#### Как тестировать порядок сообщений?

**Ответ**

Отправить несколько событий по одной сущности с одинаковым key, например order_id, и проверить, что consumer обработал их в правильном порядке. Также стоит проверить out-of-order сценарий, если система должна быть к нему устойчива.

### 43. Самое важное, что надо запомнить

Если совсем коротко, для собеседования важно:

Брокер нужен для асинхронного взаимодействия и развязки сервисов. Producer отправляет сообщение, broker его хранит/маршрутизирует, consumer обрабатывает. Основные проблемы — дубли, потеря сообщений, нарушение порядка, retry, DLQ и lag. В тестировании важно проверять не только happy path, но и ошибки: падение consumer-а, повторную доставку, идемпотентность, retry, DLQ и eventual consistency. Kafka больше про поток событий, partitions, offset, consumer groups и replay. RabbitMQ больше про очереди, exchange, routing key, ack/nack и task processing.
