# Сети и HTTP — быстрый повтор

[← Все шпаргалки](README.md) · [Подробный раздел API и HTTP](../questions/api-http.md)

## Что важно AQA/SDET

Нужно понимать путь запроса от клиента до сервиса, уметь объяснить TCP, DNS, HTTP и TLS и диагностировать, на каком участке возникла проблема.

## Уровни — коротко

| Уровень | За что отвечает | Примеры |
|---|---|---|
| прикладной | протокол приложения | HTTP, DNS, SMTP |
| транспортный | доставка между процессами | TCP, UDP, порты |
| сетевой | доставка между сетями | IP, ICMP, маршрутизация |
| канальный | доставка внутри локальной сети | Ethernet, MAC, ARP |
| физический | передача сигнала | кабель, Wi-Fi |

На собеседовании важнее понимать путь данных, чем механически перечислять семь уровней OSI.

## Что происходит при открытии сайта

1. Клиент проверяет кеш DNS и `/etc/hosts`.
2. DNS преобразует доменное имя в IP-адрес.
3. Клиент устанавливает TCP-соединение.
4. Для HTTPS выполняется TLS handshake и проверяется сертификат.
5. Клиент отправляет HTTP-запрос.
6. Запрос может пройти через CDN, load balancer, proxy или API gateway.
7. Сервер возвращает HTTP-ответ.

## IP, порт и MAC

- IP-адрес определяет сетевой интерфейс в сети;
- порт определяет приложение или сервис на хосте;
- пара `IP:port` указывает точку подключения;
- MAC используется для доставки внутри локального сегмента;
- ARP помогает узнать MAC по IPv4-адресу внутри локальной сети.

Пример: `10.0.0.15:5432` — PostgreSQL на хосте `10.0.0.15`.

## TCP и UDP

| TCP | UDP |
|---|---|
| устанавливает соединение | без установки соединения |
| гарантирует порядок и повторную передачу | таких гарантий не даёт |
| поток байтов | отдельные датаграммы |
| больше накладных расходов | меньше накладных расходов |
| HTTP/1.1 и HTTP/2 | DNS, стриминг; HTTP/3 работает поверх QUIC/UDP |

### TCP handshake

1. клиент → сервер: `SYN`;
2. сервер → клиент: `SYN-ACK`;
3. клиент → сервер: `ACK`.

## DNS

DNS преобразует доменное имя в IP-адрес.

Полезные записи:

- `A` — IPv4;
- `AAAA` — IPv6;
- `CNAME` — псевдоним;
- `MX` — почтовый сервер;
- `TXT` — текстовые данные;
- `NS` — DNS-сервер зоны.

```bash
nslookup example.com
dig example.com
dig +short example.com
```

`/etc/hosts` позволяет локально задать соответствие имени и IP до обращения к DNS.

## Частые порты

| Порт | Протокол/сервис |
|---|---|
| 22 | SSH |
| 53 | DNS |
| 80 | HTTP |
| 443 | HTTPS |
| 5432 | PostgreSQL |
| 5672 | RabbitMQ/AMQP |
| 6379 | Redis |
| 9092 | Kafka |

Порт может отличаться от стандартного.

## Ошибки соединения

- `connection refused` — хост ответил, но на порту никто не слушает либо соединение отклонено;
- `connection timeout` — ответ не пришёл вовремя: сеть, firewall, маршрут или недоступный хост;
- `connection reset by peer` — удалённая сторона принудительно закрыла соединение;
- DNS error — имя не удалось преобразовать в адрес;
- read timeout — соединение создано, но ответ не получен вовремя.

## HTTP-запрос и ответ

Запрос содержит:

- метод;
- URL;
- headers;
- необязательное тело.

Ответ содержит:

- status code;
- headers;
- необязательное тело.

## HTTP-методы

| Метод | Назначение | Safe | Идемпотентный по стандартной семантике |
|---|---|---|---|
| `GET` | получить ресурс | да | да |
| `HEAD` | получить только headers | да | да |
| `POST` | создать или запустить операцию | нет | обычно нет |
| `PUT` | полностью заменить ресурс | нет | да |
| `PATCH` | частично изменить ресурс | нет | не гарантируется |
| `DELETE` | удалить ресурс | нет | да |

Идемпотентность означает, что повтор одинакового запроса имеет тот же ожидаемый эффект на сервере, что и один запрос. Это не означает одинаковый status code или отсутствие логирования.

## Status codes

| Код | Значение |
|---|---|
| `200` | успешный ответ |
| `201` | ресурс создан |
| `202` | запрос принят в обработку |
| `204` | успешно, тела нет |
| `301/308` | постоянный redirect |
| `302/307` | временный redirect |
| `304` | использовать кешированное представление |
| `400` | некорректный запрос |
| `401` | нет корректной аутентификации |
| `403` | пользователь известен, но доступ запрещён |
| `404` | ресурс не найден |
| `409` | конфликт с текущим состоянием |
| `415` | неподдерживаемый формат тела |
| `422` | запрос понятен, но данные не проходят обработку/валидацию |
| `429` | превышен rate limit |
| `500` | внутренняя ошибка сервиса |
| `502` | gateway получил некорректный ответ upstream |
| `503` | сервис временно недоступен |
| `504` | gateway не дождался upstream |

## Headers

- `Content-Type` — формат отправляемого тела;
- `Accept` — желаемый формат ответа;
- `Authorization` — данные аутентификации;
- `Cache-Control` — правила кеширования;
- `ETag` и `If-None-Match` — условные запросы и кеш;
- `Location` — адрес созданного ресурса или redirect;
- `Retry-After` — когда повторить запрос;
- correlation/request ID — связь логов одного запроса.

## Cookies, session и token

- cookie — небольшое значение, которое браузер хранит и отправляет серверу;
- server-side session — состояние хранится на сервере, клиент передаёт идентификатор;
- token — клиент передаёт подтверждение авторизации;
- JWT — формат токена с header, payload и подписью; payload обычно не зашифрован.

У cookie важны флаги `Secure`, `HttpOnly` и `SameSite`.

## HTTPS и TLS

HTTPS — HTTP поверх TLS. TLS:

- шифрует трафик;
- проверяет целостность;
- позволяет проверить сервер по сертификату.

Проверять:

- срок действия;
- доменное имя;
- доверенную цепочку;
- корректность времени на клиенте;
- поддерживаемые версии и шифры.

```bash
openssl s_client -connect example.com:443 -servername example.com
```

## Proxy, load balancer и API gateway

- forward proxy действует от имени клиента;
- reverse proxy принимает запросы перед сервисами;
- load balancer распределяет трафик между экземплярами;
- API gateway добавляет маршрутизацию, авторизацию, rate limiting и другие политики;
- sticky session закрепляет клиента за экземпляром и может усложнять масштабирование.

## Docker networking

- `localhost` внутри контейнера указывает на этот же контейнер;
- контейнеры в одной Compose-сети обращаются друг к другу по имени сервиса;
- запись `8080:80` означает порт `8080` на хосте → порт `80` контейнера;
- чтобы сервис был доступен извне контейнера, он обычно должен слушать `0.0.0.0`, а не только `127.0.0.1`.

## Диагностика

```bash
dig +short api.example.com
ping api.example.com
traceroute api.example.com
nc -vz api.example.com 443
curl -v --connect-timeout 3 --max-time 10 https://api.example.com/health
ss -lntp
lsof -i :8080
tcpdump -i any port 443
```

Порядок проверки:

1. резолвится ли DNS;
2. достижим ли маршрут;
3. открыт ли TCP-порт;
4. проходит ли TLS;
5. какой HTTP-ответ;
6. слушает ли процесс нужный адрес и порт;
7. что в логах сервиса и proxy;
8. нет ли firewall, security group или сетевой политики.
