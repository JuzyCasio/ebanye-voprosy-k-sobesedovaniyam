# Брокеры сообщений — быстрый повтор

[← Все шпаргалки](README.md) · [Подробный раздел](../questions/api-http/message-brokers.md)

## Что такое брокер

Брокер сообщений — промежуточный сервис между отправителем и получателем. Producer отправляет сообщение брокеру, а consumer получает и обрабатывает его.

Плюсы:

- producer и consumer не обязаны работать одновременно;
- сервисы меньше зависят друг от друга;
- сообщения можно буферизовать;
- обработку можно масштабировать;
- сбои можно переживать с помощью повторов и хранения сообщений.

Минусы:

- появляется eventual consistency;
- возможны дубликаты и изменение порядка;
- сложнее диагностика;
- нужно следить за lag, очередями, ретраями и DLQ.

## Термины

| Термин | Значение |
|---|---|
| producer | отправляет сообщения |
| consumer | получает и обрабатывает |
| message/event | передаваемые данные |
| queue | очередь сообщений |
| topic | именованный поток сообщений |
| partition | часть Kafka topic |
| offset | позиция сообщения в partition |
| consumer group | группа consumers, делящих работу |
| ack | подтверждение успешной обработки |
| nack/reject | сообщение не обработано |
| retry | повторная обработка |
| DLQ | отдельное место для необработанных сообщений |

## Queue и Publish/Subscribe

- queue: одно сообщение обычно обрабатывает один consumer из группы;
- publish/subscribe: одно событие получают разные независимые подписчики;
- в Kafka разные consumer groups получают собственное логическое чтение topic, а consumers внутри одной группы делят partitions.

## Синхронность и асинхронность

При синхронном вызове клиент ждёт ответ прямо сейчас. При асинхронном взаимодействии producer обычно получает подтверждение записи, а бизнес-обработка завершается позже.

Для теста это означает: после публикации события нельзя сразу ожидать конечное состояние без ожидания условия.

## Гарантии доставки

| Гарантия | Смысл |
|---|---|
| at-most-once | сообщение может потеряться, но не должно повториться |
| at-least-once | сообщение не должно потеряться, но возможны дубликаты |
| exactly-once | эффект должен быть применён ровно один раз в оговорённых границах |

На практике часто используют at-least-once плюс идемпотентный consumer.

## Ack, Nack, Retry и DLQ

Consumer подтверждает сообщение только после успешной обработки.

Типовой поток:

1. получить сообщение;
2. проверить схему;
3. выполнить бизнес-операцию;
4. сохранить результат;
5. отправить ack или закоммитить offset.

При временной ошибке используют retry с задержкой и ограничением попыток. При постоянной ошибке сообщение отправляют в DLQ.

Без ограничения retry «ядовитое» сообщение может бесконечно возвращаться и блокировать обработку.

## Идемпотентность

Повторная обработка одного сообщения не должна повторно создавать бизнес-эффект.

Способы:

- уникальный `event_id`;
- таблица обработанных сообщений;
- уникальное ограничение в БД;
- upsert;
- проверка текущего состояния;
- идемпотентная бизнес-операция.

## Порядок сообщений

Глобальный порядок обычно дорог или не гарантируется.

- Kafka гарантирует порядок внутри одной partition;
- сообщения с одним бизнес-ключом направляют в одну partition;
- несколько consumers и retries могут менять наблюдаемый порядок;
- consumer должен уметь обнаруживать старую версию события, если порядок важен.

## Kafka — минимум

- данные записываются в topic;
- topic разделён на partitions;
- сообщение в partition имеет offset;
- consumer group делит partitions между consumers;
- один partition внутри группы в момент времени читает один consumer;
- сообщение не удаляется сразу после чтения, а хранится по retention;
- commit offset фиксирует позицию группы;
- lag показывает, насколько consumer отстаёт.

Безопасный базовый порядок consumer:

1. получить запись;
2. обработать;
3. сохранить результат;
4. после успеха закоммитить offset.

## RabbitMQ — минимум

- producer публикует сообщение в exchange;
- exchange маршрутизирует его в queue по bindings;
- consumer читает queue;
- manual ack подтверждает успешную обработку;
- nack/reject может вернуть сообщение в queue или отправить его в dead-letter exchange;
- prefetch ограничивает количество неподтверждённых сообщений у consumer.

Типы exchange:

| Тип | Маршрутизация |
|---|---|
| direct | точное совпадение routing key |
| topic | совпадение по шаблону |
| fanout | во все связанные queues |
| headers | по headers |

## Kafka и RabbitMQ

| Kafka | RabbitMQ |
|---|---|
| распределённый журнал событий | классический брокер очередей |
| хранит записи по retention | сообщение обычно удаляется после ack |
| чтение по offset | доставка из queue |
| порядок внутри partition | порядок queue может нарушаться параллельной обработкой/retry |
| удобен для event streaming и replay | удобен для задач, маршрутизации и request/reply |

Выбор зависит от требований, а не от того, какой брокер «лучше».

## Что тестировать

### Producer

- правильный topic/queue/exchange;
- ключ и headers;
- схема и обязательные поля;
- уникальный event ID;
- поведение при недоступном брокере;
- retry и timeout.

### Маршрутизация

- правильный routing key;
- нужная queue или partition;
- неизвестный маршрут;
- несколько подписчиков;
- права доступа.

### Consumer

- успешная обработка;
- невалидная схема;
- дубликат;
- временная ошибка и retry;
- постоянная ошибка и DLQ;
- порядок событий;
- повтор после падения до ack/commit;
- неизвестная версия события.

### End-to-end

Проверять не только наличие сообщения, но и конечный бизнес-эффект: запись в БД, изменение статуса, вызов другого сервиса.

## Как ждать асинхронный результат

Плохо:

```python
time.sleep(10)
assert get_status(order_id) == "processed"
```

Лучше опрашивать состояние до deadline:

```python
from time import monotonic, sleep


def wait_until_processed(get_status, order_id, timeout=10):
    deadline = monotonic() + timeout
    while monotonic() < deadline:
        if get_status(order_id) == "processed":
            return
        sleep(0.2)
    raise AssertionError("Order was not processed in time")
```

Ожидание должно иметь timeout и полезную диагностику.

## Тестовые данные

- уникальный correlation ID;
- уникальный event ID;
- отдельный consumer group для тестового запуска;
- уникальные бизнес-сущности;
- очистка созданных данных;
- фильтрация сообщений своего теста;
- отсутствие зависимости от чужих сообщений в общей среде.

## Schema evolution

Проверять:

- добавление необязательного поля;
- отсутствие нового поля у старого producer;
- неизвестные дополнительные поля;
- смену типа;
- удаление или переименование поля;
- поддержку нескольких версий.

Совместимость контракта часто важнее точного совпадения всего JSON.

## Transactional outbox

Проблема: сервис сохранил данные в БД, но упал до публикации события.

Outbox решает её так:

1. бизнес-изменение и запись события сохраняются в одной транзакции БД;
2. отдельный publisher читает outbox и отправляет события;
3. после успеха запись помечается отправленной.

## Наблюдаемость

Следить за:

- размером queue;
- consumer lag;
- скоростью публикации и обработки;
- возрастом старейшего сообщения;
- количеством retry и DLQ;
- ошибками producer/consumer;
- rebalance и недоступными partitions;
- correlation ID в логах и трассировке.

## Частые ошибки тестов

- `sleep()` вместо ожидания;
- чтение чужого сообщения;
- подтверждение сообщения до проверки;
- отсутствие проверки дубликатов;
- бесконечный retry;
- один consumer group для параллельных тестов;
- проверка только факта публикации без бизнес-эффекта;
- очистка queue, которой пользуются другие тесты.
