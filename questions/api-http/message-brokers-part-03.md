## 8. Retry

Retry — повторная попытка обработки сообщения.  

Например:  

Consumer не смог вызвать внешний API.  
Через 10 секунд пробует снова.  
Потом через 1 минуту.  
Потом через 5 минут.  
Какие бывают retry  
Immediate retry  

Повтор сразу.  

### Плохо, если проблема временная:

Сервис оплаты лежит.  
Consumer будет бесконечно долбить его запросами.  
Delayed retry  

Повтор через задержку.  

1-я попытка  
через 10 сек  
через 1 мин  
через 5 мин  
Exponential backoff  

Задержка растёт постепенно.  

1 сек  
2 сек  
4 сек  
8 сек  
16 сек  

Это снижает нагрузку на проблемный сервис.  

### Что тестировать в retry

Проверять:  

что сообщение повторяется при временной ошибке;  
что количество попыток ограничено;  
что между попытками есть задержка;  
что после исчерпания попыток сообщение уходит в DLQ;  
что успешная повторная обработка не создаёт дублей.  

## 9. DLQ — Dead Letter Queue

DLQ — очередь для сообщений, которые не удалось обработать.  

Туда попадают сообщения, если:  

превышено количество retry;  
сообщение невалидное;  
consumer постоянно падает;  
истёк TTL;  
произошла бизнес-ошибка.  

### Пример:

orders.created -> consumer -> ошибка -> retry -> retry -> retry -> DLQ  

DLQ нужна, чтобы:  

не терять проблемные сообщения;  
не блокировать основную очередь;  
расследовать причины ошибок;  
переобработать сообщения вручную.  
Что должно быть в DLQ-сообщении  

Желательно сохранять:  

исходный payload;  
headers;  
причину ошибки;  
количество попыток;  
время первой ошибки;  
время последней ошибки;  
название consumer-а;  
correlation_id / trace_id.  

## 10. Poison message

Poison message — сообщение, которое всегда ломает обработчик.  

Например:  

{  
  "order_id": null,  
  "amount": "abc"  
}  

Если его постоянно возвращать в очередь, оно может заблокировать обработку.  

### Решение:

ограничить retry;  
отправлять в DLQ;  
валидировать схему;  
логировать причину.  

## 11. Idempotency

Идемпотентность — возможность безопасно обработать одно и то же сообщение несколько раз без изменения результата после первого успешного выполнения.  

### Пример неидемпотентной обработки:

Получили message payment_completed.  
Начислили пользователю 100 бонусов.  
Получили дубль.  
Начислили ещё 100 бонусов.  
Ошибка.  

### Пример идемпотентной обработки:

Проверили event_id.  
Если такой event_id уже обработан — пропускаем.  
Если нет — начисляем бонусы и сохраняем event_id.  
Почему идемпотентность важна  

Потому что при at least once delivery дубли возможны почти всегда.  

Причины дублей:  

consumer обработал сообщение, но не отправил ack;  
producer повторно отправил сообщение;  
брокер переотдал сообщение после сбоя;  
произошёл rebalance;  
network timeout;  
retry на стороне producer-а.  
Как обеспечить идемпотентность  

Способы:  

Уникальный event_id/message_id  
хранить обработанные id.  
Уникальный бизнес-ключ  
например order_id + event_type.  
Уникальный constraint в БД  
например event_id UNIQUE.  
Проверка состояния  
если заказ уже PAID, повторно не списывать деньги.  
Transactional outbox  
событие и изменение бизнес-сущности сохраняются атомарно.  

## 12. Ordering — порядок сообщений

Порядок сообщений — сложная тема.  

### Где порядок важен

Например:  

order_created  
order_paid  
order_cancelled  

Нельзя обработать order_paid раньше, чем order_created, если логика этого не допускает.  

Kafka  

В Kafka порядок гарантирован только внутри одной partition.  

Чтобы события одного заказа шли в правильном порядке, используют один и тот же key:  

key = order_id  

Тогда все события по одному заказу попадут в одну partition.  

order_id=777 -> partition 1  
RabbitMQ  

В RabbitMQ порядок в очереди может сохраняться, но если у тебя несколько consumers, порядок обработки может нарушиться.  

### Пример:

msg1 забрал Consumer A  
msg2 забрал Consumer B  

Consumer B обработал быстрее.  
msg2 завершился раньше msg1.  
Хороший ответ на собеседовании  

Если порядок критичен, нужно проектировать это явно: например, в Kafka использовать key, чтобы события одной сущности попадали в одну partition. Также важно помнить, что при параллельной обработке порядок может нарушаться, поэтому consumer должен быть готов к out-of-order событиям или обработка должна быть сериализована для конкретного ключа.
