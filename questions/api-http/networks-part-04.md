## 28. 401 vs 403

Очень частый вопрос.  

401 Unauthorized  

Пользователь не аутентифицирован.  

### Пример:

Нет токена  
Токен невалидный  
Токен истек  
403 Forbidden  

Пользователь аутентифицирован, но прав не хватает.  

### Пример:

Пользователь залогинен, но не имеет роли admin  
Как сказать на собесе  

401 — система не понимает, кто ты, или токен невалидный. 403 — система понимает, кто ты, но доступ к ресурсу запрещен.  

## 29. 400 vs 422

400 Bad Request  

Запрос некорректный технически:  

битый JSON;  
неправильный формат;  
отсутствует обязательный header;  
некорректный синтаксис.  
422 Unprocessable Entity  

Запрос синтаксически корректный, но бизнес-валидация не прошла.  

### Пример:

{  
  "email": "not-email"  
}  

JSON валидный, но email неправильный.  

## 30. 502 vs 503 vs 504

Очень важный блок.  

502 Bad Gateway  

Прокси/gateway получил некорректный ответ от upstream-сервера.  

### Пример:

nginx -> backend  
backend вернул битый ответ или закрыл соединение  
503 Service Unavailable  

Сервис временно недоступен.  

Причины:  

сервис перегружен;  
сервис на maintenance;  
нет доступных backend-инстансов;  
приложение не готово принимать трафик.  
504 Gateway Timeout  

Gateway/proxy не дождался ответа от upstream.  

### Пример:

nginx ждал ответ от backend, но backend слишком долго отвечал  
Как запомнить  
Код	Простыми словами  
502	backend ответил плохо  
503	backend недоступен  
504	backend слишком долго молчит  

## 31. HTTP headers

Headers — метаданные запроса/ответа.  

Частые request headers  
Header	Назначение  
Host	домен сервера  
User-Agent	клиент  
Accept	какой формат ответа ожидаем  
Content-Type	формат тела запроса  
Authorization	авторизация  
Cookie	cookies  
X-Request-ID	идентификатор запроса  
X-Forwarded-For	реальный IP клиента за proxy  
X-Forwarded-Proto	исходный протокол HTTP/HTTPS  
Частые response headers  
Header	Назначение  
Content-Type	формат ответа  
Content-Length	размер тела  
Set-Cookie	установить cookie  
Cache-Control	правила кэширования  
Location	адрес для redirect  
Retry-After	когда повторить запрос  
Server	сервер  
Date	дата ответа  

## 32. Content-Type vs Accept

Content-Type  

Говорит, в каком формате тело запроса или ответа.  

### Пример:

Content-Type: application/json  
Accept  

Говорит, какой формат клиент хочет получить.  

### Пример:

Accept: application/json  
Разница  

Content-Type описывает то, что отправляем. Accept описывает то, что хотим получить.  

## 33. Cookies

Cookie — небольшие данные, которые сервер сохраняет на стороне клиента.  

Сервер отправляет:  

Set-Cookie: session_id=abc123; HttpOnly; Secure  

Клиент потом отправляет:  

Cookie: session_id=abc123  
Атрибуты cookie  
Атрибут	Значение  
HttpOnly	недоступна из JavaScript  
Secure	передается только по HTTPS  
SameSite	ограничивает отправку cookie между сайтами  
Expires/Max-Age	срок жизни  
Domain	домен  
Path	путь  

## 34. Session vs Token

Session-based auth  

Сервер хранит сессию у себя.  
Клиент хранит cookie с session_id.  

### Плюсы:

можно легко инвалидировать сессию;  
удобно для веб-приложений.  

### Минусы:

серверу нужно хранить состояние;  
сложнее масштабировать без общего session storage.  
Token-based auth  

Клиент хранит токен, например JWT.  

### Плюсы:

stateless;  
удобно для API и микросервисов.  

### Минусы:

сложнее мгновенно отозвать токен;  
нужно аккуратно работать со сроком жизни.  

## 35. JWT

JWT — JSON Web Token.  

Состоит из трех частей:  

header.payload.signature  

### Пример структуры:

xxxxx.yyyyy.zzzzz  
Header  

Информация об алгоритме.  

Payload  

Данные/claims:  

{  
  "user_id": 123,  
  "role": "admin",  
  "exp": 1710000000  
}  
Signature  

Подпись, чтобы проверить, что токен не подменили.  

### Важно

JWT обычно не шифрует payload, а только подписывает. Поэтому не стоит класть туда чувствительные данные.  

## 36. HTTPS и TLS

HTTPS = HTTP поверх TLS.  

TLS обеспечивает:  

шифрование;  
проверку подлинности сервера;  
целостность данных.  
Что происходит при HTTPS  
Клиент подключается к серверу.  
Начинается TLS handshake.  
Сервер отправляет сертификат.  
Клиент проверяет сертификат.  
Клиент и сервер договариваются о ключах.  
Дальше HTTP идет в зашифрованном канале.
