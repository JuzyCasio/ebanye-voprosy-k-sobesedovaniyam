## 129. Как отвечать на вопрос “В Docker контейнере не подключается к БД”

Проверю, в одной ли Docker-сети контейнеры, правильно ли указан host. Частая ошибка — использовать localhost внутри контейнера. Для подключения к другому сервису в docker-compose нужно использовать имя сервиса, например postgres:5432.  

## 130. Как отвечать на вопрос “Что такое timeout и какие бывают?”

Timeout — это ограничение времени ожидания операции. Бывает connect timeout, когда не удалось установить соединение, read timeout, когда соединение есть, но нет ответа, write timeout, когда не получается отправить данные, и gateway timeout, когда proxy не дождался backend.  

## 131. Как отвечать на вопрос “Как тестировать сетевые сбои?”

Можно использовать mock-сервисы, которые возвращают ошибки или задерживают ответ, останавливать зависимости в Docker, настраивать короткие timeout’ы клиента, проверять retry logic, idempotency и корректность пользовательской ошибки. Важно не просто вызвать сбой, а проверить, что система корректно деградирует.

## 133. Мини-шпаргалка “ответить коротко”

TCP  

Надежный транспортный протокол с соединением, гарантирует доставку и порядок.  

UDP  

Быстрый транспортный протокол без соединения и гарантий доставки.  

DNS  

Переводит доменное имя в IP.  

NAT  

Подменяет IP-адреса, часто нужен для выхода приватных сетей в интернет.  

Proxy  

Посредник между клиентом и сервером.  

Reverse proxy  

Стоит перед backend и маршрутизирует входящие запросы.  

Load balancer  

Распределяет нагрузку между несколькими backend-серверами.  

TLS  

Шифрует соединение и проверяет подлинность сервера.  

CORS  

Браузерный механизм, который контролирует междоменные запросы.  

401  

Не аутентифицирован.  

403  

Аутентифицирован, но нет прав.  

502  

Gateway получил плохой ответ от backend.  

503  

Сервис временно недоступен.  

504  

Gateway не дождался backend.  

Connection refused  

На порту никто не слушает или соединение отклонено.  

Timeout  

Ответ не пришел за заданное время.  

localhost в Docker  

Это сам контейнер, а не хост и не соседний контейнер.  

## 134. Мини-практика для самопроверки

Попробуй ответить вслух.  

Вопрос 1  

### Что происходит при открытии https://example.com?

### Хороший ответ должен содержать:

DNS -> TCP handshake -> TLS handshake -> HTTP request -> HTTP response  
Вопрос 2  

### Почему ping работает, а curl нет?

### Хороший ответ:

ping проверяет ICMP/host, curl проверяет HTTP/TCP порт и приложение  
Вопрос 3  

Чем 502 отличается от 504?  

502 — плохой ответ от upstream  
504 — upstream не ответил вовремя  
Вопрос 4  

### Почему из контейнера не работает localhost:5432?

localhost внутри контейнера — это сам контейнер  
Вопрос 5  

### Что проверишь при connection refused?

запущен ли сервис, слушает ли порт, правильный host/port, firewall  
Вопрос 6  

### Что проверишь при DNS error?

dig/nslookup, /etc/hosts, /etc/resolv.conf, VPN, DNS-сервер  

## 135. Самый сильный ответ для QA Automation

Можно использовать как универсальный ответ:  

В сетевых проблемах я стараюсь идти по слоям. Сначала проверяю, резолвится ли домен через DNS, потом доступен ли хост и маршрут, затем открыт ли нужный TCP-порт, после этого проверяю HTTP/TLS через curl. Если соединение есть, но API возвращает ошибку, смотрю status code, headers, body, request-id и логи backend/proxy. В Docker отдельно проверяю сеть контейнеров, port mapping и не используется ли ошибочно localhost.  

Это прям хороший ответ уровня уверенного QA/SDET.
