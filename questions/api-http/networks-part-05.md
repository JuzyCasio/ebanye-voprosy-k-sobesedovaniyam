## 37. TLS certificate

Сертификат подтверждает, что сервер действительно принадлежит нужному домену.  

Проверяется:  

домен в сертификате;  
срок действия;  
цепочка доверия;  
доверенный CA;  
не отозван ли сертификат.  
Частые проблемы  
certificate expired  
self-signed certificate  
hostname mismatch  
unable to verify first certificate  
Проверить сертификат  
openssl s_client -connect example.com:443 -servername example.com  

## 38. HTTP vs HTTPS

HTTP	HTTPS  
Без шифрования	Шифрование через TLS  
Обычно порт 80	Обычно порт 443  
Данные можно перехватить	Данные защищены  
Не проверяет сервер	Проверяет сертификат сервера  

## 39. HTTP/1.1, HTTP/2, HTTP/3

HTTP/1.1  
текстовый протокол;  
один запрос/ответ за раз на соединение;  
keep-alive позволяет переиспользовать соединение;  
возможен head-of-line blocking.  
HTTP/2  
бинарный протокол;  
мультиплексирование;  
несколько запросов в одном TCP-соединении;  
сжатие headers;  
используется gRPC.  
HTTP/3  
работает поверх QUIC;  
QUIC работает поверх UDP;  
быстрее устанавливает соединения;  
лучше переносит потери пакетов.  
На собесе  

HTTP/2 позволяет отправлять несколько параллельных запросов в одном TCP-соединении за счет мультиплексирования. HTTP/3 использует QUIC поверх UDP.  

## 40. REST

REST — архитектурный стиль для API.  

### Идея:

ресурсы представлены URL;  
используются HTTP-методы;  
stateless;  
стандартные status codes;  
часто JSON.  

### Пример:

GET /users/1  
POST /users  
PUT /users/1  
DELETE /users/1  
Stateless  

Каждый запрос должен содержать всё необходимое для обработки.  

Сервер не должен зависеть от состояния предыдущего запроса.  

## 41. REST vs RPC

REST  

Ориентирован на ресурсы:  

GET /users/1  
POST /orders  
RPC  

Ориентирован на действия:  

POST /createUser  
POST /calculatePrice  
На собесе  

В REST мы работаем с ресурсами через стандартные HTTP-методы. В RPC чаще вызываем конкретные операции или методы.  

## 42. gRPC

gRPC — RPC-фреймворк, который обычно работает поверх HTTP/2 и использует Protocol Buffers.  

Особенности  
строгие контракты через .proto;  
бинарный формат;  
быстрее JSON в некоторых сценариях;  
поддерживает streaming;  
удобен для микросервисов.  
gRPC vs REST  
gRPC	REST  
HTTP/2	чаще HTTP/1.1 или HTTP/2  
Protobuf	JSON  
строгий контракт	часто OpenAPI  
быстрее и компактнее	проще читать руками  
хорошо для service-to-service	удобно для публичных API  

## 43. WebSocket

WebSocket — протокол для постоянного двустороннего соединения между клиентом и сервером.  

Используется для:  

чатов;  
уведомлений;  
real-time данных;  
торговых терминалов;  
онлайн-игр.  
Как работает  

Сначала идет HTTP-запрос с upgrade:  

Upgrade: websocket  
Connection: Upgrade  

Потом соединение становится WebSocket.  

## 44. Long polling vs WebSocket

Long polling  

Клиент отправляет запрос, сервер держит его открытым до появления события.  

WebSocket  

Открывается постоянное двустороннее соединение.  

Long polling	WebSocket  
Много HTTP-запросов	Одно постоянное соединение  
Проще	Эффективнее для real-time  
Подходит для редких событий	Подходит для частых событий  

## 45. Proxy

Proxy — посредник между клиентом и сервером.  

Forward proxy  

Работает на стороне клиента.  

### Пример:

Клиент -> Proxy -> Интернет  

Используется:  

корпоративный доступ в интернет;  
фильтрация;  
анонимизация;  
кэширование.  
Reverse proxy  

Работает на стороне сервера.  

### Пример:

Клиент -> Nginx -> Backend  

Используется:  

балансировка;  
TLS termination;  
маршрутизация;  
кэширование;  
rate limiting.  

## 46. Load Balancer

Load balancer распределяет запросы между несколькими backend-серверами.  

Client -> Load Balancer -> Backend 1  
                         -> Backend 2  
                         -> Backend 3  
Алгоритмы балансировки  
Алгоритм	Идея  
Round Robin	по очереди  
Least Connections	туда, где меньше соединений  
IP Hash	один клиент чаще попадает на один backend  
Weighted	с учетом веса сервера  
Что важно для QA  

При тестировании может быть проблема:  

один backend обновился, другой нет;  
sticky sessions;  
разные версии приложения;  
состояние есть только на одном инстансе;  
intermittent bugs.  

## 47. Sticky sessions

Sticky session — когда клиента направляют на один и тот же backend.  

Зачем:  

если сессия хранится локально на backend;  
чтобы пользователь не “прыгал” между инстансами.  

### Проблема:

при падении backend сессия может потеряться;  
неравномерная нагрузка;  
сложнее масштабировать.
