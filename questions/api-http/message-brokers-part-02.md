## 4. Синхронное vs асинхронное взаимодействие

Синхронное  

Сервис ждёт ответ сразу.  

Client -> API -> Payment Service  
             <- response  

### Плюсы:

проще понимать результат;  
проще обрабатывать ошибки;  
хорошо для запросов “дай данные сейчас”.  

### Минусы:

сильная связность;  
если сервис недоступен, операция падает;  
хуже переносит пики нагрузки.  
Асинхронное  

Сервис отправил сообщение и не ждёт моментальной обработки.  

Order Service -> Broker -> Notification Service  

### Плюсы:

слабая связность;  
лучше отказоустойчивость;  
можно обрабатывать позже;  
хорошо масштабируется.  

### Минусы:

сложнее тестировать;  
сложнее отлаживать;  
eventual consistency;  
нужны retry, DLQ, idempotency.  

## 5. Event-driven architecture

Event-driven architecture — архитектура, где сервисы реагируют на события.  

### Пример события:

order_created  
payment_completed  
user_registered  
document_verified  

Сервис не говорит другому сервису:  

"Отправь письмо"  

Он говорит:  

"Пользователь зарегистрировался"  

А другие сервисы сами решают, что делать.  

Command vs Event  

Это частый вопрос на собеседовании.  

Command  

### Команда — просьба что-то сделать.

CreateUser  
SendEmail  
ReserveProduct  

Обычно команда адресована конкретному обработчику.  

Event  

Событие — факт, который уже произошёл.  

UserCreated  
OrderPaid  
ProductReserved  

Событие не просит ничего сделать, оно просто сообщает о факте.  

### Хорошая формулировка для собеседования:

Command — это намерение выполнить действие, а Event — это факт, что действие уже произошло. Например, CreateOrder — команда, а OrderCreated — событие.  

## 6. Delivery semantics

Это одна из самых важных тем.  

Delivery semantics — это гарантии доставки сообщений.  

At most once  

Не более одного раза.  

Сообщение может быть потеряно, но не будет обработано дважды.  

Producer отправил сообщение.  
Consumer получил.  
Consumer упал до обработки.  
Сообщение потеряно.  

### Плюсы:

быстро;  
просто.  

### Минусы:

возможна потеря данных.  

Используется там, где потеря не критична:  

метрики;  
логи;  
неважная аналитика.  
At least once  

### Как минимум один раз.

Сообщение не должно потеряться, но может быть обработано повторно.  

Consumer получил сообщение.  
Обработал его.  
Но не успел отправить ack.  
Брокер отдаёт сообщение снова.  

### Плюсы:

сообщение почти не теряется;  
надёжнее.  

### Минусы:

возможны дубли.  

Это самый частый вариант в реальных системах.  

Требует:  

идемпотентности;  
дедупликации;  
уникальных message_id/event_id.  
Exactly once  

Ровно один раз.  

В идеале сообщение обрабатывается ровно один раз.  

Но на практике это сложная гарантия.  

### Часто на собеседовании лучше сказать так:

Exactly once в распределённых системах сложно обеспечить полностью. Обычно брокер может дать определённые гарантии на уровне доставки или записи, но бизнес-обработка всё равно должна быть идемпотентной.  

Kafka поддерживает exactly-once semantics для некоторых сценариев, например producer transactions + idempotent producer + корректная обработка offsets. Но на уровне внешней БД или внешнего API всё равно могут быть повторы.  

## 7. Ack / Nack

Ack  

Ack — подтверждение, что сообщение успешно обработано.  

Consumer получил сообщение  
Consumer обработал сообщение  
Consumer отправил ack  
Broker удалил/пометил сообщение как обработанное  
Nack  

Nack — отрицательное подтверждение.  

Consumer говорит:  

Я не смог обработать сообщение  

После этого брокер может:  

вернуть сообщение в очередь;  
отправить в retry queue;  
отправить в DLQ;  
удалить сообщение.  
Auto ack vs Manual ack  
Auto ack  

Сообщение считается обработанным сразу после получения consumer-ом.  

Минус:  

Consumer получил сообщение и сразу упал.  
Брокер считает сообщение обработанным.  
Сообщение потеряно.  
Manual ack  

Consumer сам подтверждает успешную обработку.  

Это надёжнее.  

### Хороший ответ:

Для критичных операций лучше использовать manual ack: сначала обработать сообщение, сохранить результат, а потом подтвердить брокеру успешную обработку.
