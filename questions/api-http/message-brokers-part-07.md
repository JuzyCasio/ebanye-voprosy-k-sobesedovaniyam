## 23. Основные проблемы брокеров

Дубли сообщений  

Причины:  

retry;  
consumer упал до ack;  
producer отправил повторно;  
rebalance;  
network timeout.  

### Что делать:

event_id;  
идемпотентность;  
deduplication;  
уникальные constraints.  
Потеря сообщений  

Причины:  

auto ack;  
неправильный commit offset;  
неперсистентные сообщения;  
producer не дождался подтверждения;  
брокер упал до записи на диск;  
неправильные настройки retention/TTL.  

### Что делать:

manual ack;  
persistent messages;  
durable queues;  
acks=all в Kafka;  
мониторинг;  
DLQ;  
retry.  
Нарушение порядка  

Причины:  

несколько consumers;  
несколько partitions;  
retry;  
параллельная обработка;  
out-of-order delivery.  

### Что делать:

key по бизнес-сущности;  
один consumer/worker на ключ;  
версионирование событий;  
проверка состояния;  
обработка out-of-order.  
Зависание сообщений  

Причины:  

consumer упал;  
consumer не ack-ает;  
prefetch слишком большой;  
poison message;  
бесконечные retry.  

### Что делать:

timeout;  
retry limit;  
DLQ;  
monitoring;  
health checks.  
Рост очереди / lag  

Причины:  

producer быстрее consumer-а;  
consumer медленный;  
БД тормозит;  
внешний сервис недоступен;  
мало partitions/consumers.  

### Что делать:

масштабировать consumers;  
увеличить partitions;  
оптимизировать код;  
добавить batching;  
ограничить producer;  
проверить зависимости.  

## 24. Тестирование брокеров

Для QA/SDET это самая важная часть.  

Что тестировать  
1. Producer  

Проверяем:  

сообщение отправляется в нужный topic/queue;  
payload корректный;  
headers корректные;  
routing key корректный;  
message key корректный;  
event_id уникальный;  
schema соответствует контракту;  
при ошибке отправки есть retry;  
producer не теряет сообщения.  
2. Broker routing  

Проверяем:  

сообщение попадает в правильную очередь;  
неправильный routing key не доставляет сообщение;  
fanout доставляет во все очереди;  
topic exchange маршрутизирует по шаблонам;  
DLQ настроена корректно;  
TTL работает;  
retry queue работает.  
3. Consumer  

Проверяем:  

consumer читает сообщение;  
правильно обрабатывает payload;  
сохраняет результат в БД;  
отправляет ack только после успешной обработки;  
при ошибке не ack-ает сообщение;  
сообщение повторяется;  
после лимита retry уходит в DLQ;  
повторная обработка не создаёт дублей;  
consumer корректно работает после рестарта.  
4. End-to-end  

Проверяем полный бизнес-флоу:  

Создали заказ через API  
Сервис отправил событие order_created  
Consumer обработал событие  
В БД появился нужный результат  
Пользователь получил уведомление  
5. Негативные сценарии  

Проверяем:  

невалидный JSON;  
отсутствует обязательное поле;  
неизвестный event_type;  
неправильная версия схемы;  
дубль event_id;  
consumer падает во время обработки;  
брокер временно недоступен;  
БД недоступна;  
внешний API возвращает 500;  
превышен timeout;  
сообщение слишком большое;  
нарушен порядок событий.  

## 25. Пример тест-кейсов

Сценарий: заказ создан, событие отправлено  

Дано:  

Пользователь создаёт заказ через API  

Когда:  

POST /orders  

Тогда:  

В Kafka topic orders.created появляется сообщение  
Сообщение содержит order_id, user_id, amount, created_at  
event_id уникальный  
key равен order_id  
Сценарий: consumer обработал событие  

Дано:  

В topic orders.created опубликовано валидное сообщение  

Когда:  

Notification consumer получил сообщение  

Тогда:  

В БД появилась запись об уведомлении  
Сообщение ack-нуто  
Повторной обработки нет  
Сценарий: consumer упал до ack  

Дано:  

Consumer получил сообщение  

Когда:  

Consumer падает до отправки ack  

Тогда:  

Сообщение не считается обработанным  
После восстановления consumer получает сообщение повторно  
Дубли бизнес-операции не создаются  
Сценарий: poison message  

Дано:  

В очередь попало сообщение без обязательного поля order_id  

Когда:  

Consumer пытается обработать сообщение  

Тогда:  

Сообщение ретраится заданное количество раз  
После этого попадает в DLQ  
В логах есть причина ошибки  
Основная очередь не блокируется  
Сценарий: проверка идемпотентности  

Дано:  

Одно и то же сообщение с одинаковым event_id отправлено дважды  

Когда:  

Consumer обработал оба сообщения  

Тогда:  

Бизнес-операция выполнена один раз  
Второе сообщение проигнорировано или помечено как duplicate
