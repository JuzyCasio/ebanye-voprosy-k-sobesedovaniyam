## 39. Тестирование в Agile/Scrum

QA участвует не только в конце спринта.  

### Хороший QA:

участвует в refinement;  
задаёт вопросы по требованиям;  
помогает определить acceptance criteria;  
думает о рисках;  
готовит тесты заранее;  
тестирует фичу по мере готовности;  
автоматизирует регрессию;  
анализирует баги;  
участвует в ретроспективе.  

### Короткий ответ:

QA должен подключаться как можно раньше, ещё на этапе требований. Это помогает находить проблемы до разработки, а не только после неё.  

## 40. Definition of Ready и Definition of Done

Definition of Ready  

Задача готова к разработке, если:  

требования понятны;  
acceptance criteria описаны;  
макеты есть;  
зависимости известны;  
риски понятны;  
задача оценена.  
Definition of Done  

Задача готова, если:  

код написан;  
code review пройден;  
unit-тесты есть;  
тестирование выполнено;  
баги исправлены;  
документация обновлена;  
фича задеплоена на нужное окружение;  
acceptance criteria выполнены.  

## 41. Acceptance Criteria

Acceptance criteria — условия, по которым понятно, что задача выполнена.  

### Пример:

Given пользователь находится на странице логина  
When он вводит валидный email и пароль  
And нажимает кнопку Login  
Then он попадает в личный кабинет  
And видит своё имя в правом верхнем углу  

### Хорошие acceptance criteria:

конкретные;  
проверяемые;  
понятные;  
не противоречат друг другу;  
покрывают позитивные и негативные сценарии.  

## 42. BDD

BDD — Behavior Driven Development.  

### Идея:

описывать поведение системы на понятном языке;  
использовать Given/When/Then;  
связывать бизнес, разработку и тестирование.  

### Пример:

Feature: Login  

  Scenario: Successful login  
    Given registered user exists  
    When user logs in with valid credentials  
    Then dashboard page is opened  

### Плюсы:

понятность для бизнеса;  
документация в виде сценариев;  
удобно для acceptance tests.  

### Минусы:

если плохо поддерживать, превращается в лишний слой сложности;  
не стоит описывать слишком технические шаги.  

## 43. Валидация и верификация

Verification  

Проверяем, правильно ли мы создаём продукт.  

### Примеры:

review требований;  
code review;  
проверка дизайна;  
статический анализ.  
Validation  

Проверяем, тот ли продукт мы создаём.  

### Примеры:

пользовательское тестирование;  
acceptance testing;  
проверка бизнес-сценариев.  

### Короткий ответ:

Verification — соответствие спецификации. Validation — соответствие реальным потребностям пользователя.  

## 44. Черный, белый и серый ящик

Black-box testing  

Тестировщик не знает внутреннюю реализацию.  

Проверяет:  

входные данные;  
выходные данные;  
поведение системы.  
White-box testing  

Тестировщик знает внутреннюю реализацию.  

Проверяет:  

код;  
ветвления;  
условия;  
покрытие;  
внутреннюю логику.  
Grey-box testing  

### Частично знает внутреннюю реализацию.

Например:  

знает структуру БД;  
смотрит логи;  
понимает архитектуру;  
проверяет API и UI вместе.  

## 45. Тестовое покрытие

Покрытие может быть разным.  

Requirements coverage  

Какая часть требований покрыта тестами.  

Code coverage  

Какая часть кода выполнена тестами.  

### Виды:

line coverage;  
branch coverage;  
statement coverage;  
condition coverage.  

### Важно:

100% code coverage не означает отсутствие багов.  

### Пример:

def is_adult(age: int) -> bool:  
    return age >= 18  

Можно выполнить строку один раз с age=20, получить 100% line coverage, но не проверить границу 18.  

## 46. Метрики тестирования

Полезные метрики:  

количество найденных дефектов;  
дефекты по severity;  
дефекты по модулям;  
defect leakage;  
defect density;  
pass rate;  
fail rate;  
flaky rate;  
automation coverage;  
test execution time;  
mean time to detect;  
mean time to fix;  
escaped defects;  
regression duration.  

Осторожно:  

Метрики должны помогать принимать решения, а не превращаться в гонку за красивыми цифрами.  

## 47. Defect Leakage

Defect leakage — дефекты, которые прошли через тестирование и были найдены позже, например на production.  

### Пример:

QA не нашёл баг;  
баг попал на prod;  
пользователь пожаловался.  

Это повод анализировать:  

почему не было теста;  
были ли требования;  
почему автотесты не поймали;  
нужно ли добавить проверку;  
была ли проблема в процессе.
