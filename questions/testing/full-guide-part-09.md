## 27. Page Object

Page Object — паттерн для UI-автотестов.  

### Идея:

локаторы и действия страницы хранятся в отдельном классе;  
тесты не знают деталей UI;  
тесты читаются как бизнес-сценарии.  

### Пример:

from selenium.webdriver.common.by import By  
from selenium.webdriver.remote.webdriver import WebDriver  

class LoginPage:  
    def __init__(self, driver: WebDriver) -> None:  
        self.driver = driver  

    @property  
    def email_input(self):  
        return self.driver.find_element(By.CSS_SELECTOR, "[data-testid='email']")  

    @property  
    def password_input(self):  
        return self.driver.find_element(By.CSS_SELECTOR, "[data-testid='password']")  

    @property  
    def submit_button(self):  
        return self.driver.find_element(By.CSS_SELECTOR, "[data-testid='login-submit']")  

    def open(self) -> None:  
        self.driver.get("https://example.com/login")  

    def login(self, email: str, password: str) -> None:  
        self.email_input.send_keys(email)  
        self.password_input.send_keys(password)  
        self.submit_button.click()  

Тест:  

def test_user_can_login(login_page: LoginPage) -> None:  
    login_page.open()  
    login_page.login("user@example.com", "Password123")  
    assert "dashboard" in login_page.driver.current_url  

## 28. Тестовая пирамида

Классическая пирамида:  

          UI / E2E  
        Integration  
      Unit / Component  
Unit-тестов много  

Они:  

быстрые;  
дешёвые;  
стабильные;  
проверяют бизнес-логику.  
Integration/API — меньше  

Они:  

проверяют взаимодействие компонентов;  
медленнее unit;  
полезны для backend.  
UI/E2E — ещё меньше  

Они:  

самые дорогие;  
медленные;  
хрупкие;  
но проверяют путь пользователя.  

### Короткий ответ:

Чем ниже уровень тестов, тем они быстрее и дешевле. Чем выше — тем ближе к реальному пользователю, но дороже в поддержке. Поэтому большинство проверок лучше делать на unit/API/integration уровне, а UI оставить для критичных бизнес-сценариев.  

## 29. Что автоматизировать

Автоматизировать стоит:  

стабильные сценарии;  
частую регрессию;  
критичные бизнес-процессы;  
API;  
проверки с большим количеством данных;  
smoke;  
интеграционные проверки;  
трудоёмкие ручные проверки;  
проверки, которые часто повторяются.  

Не всегда стоит автоматизировать:  

разовые проверки;  
нестабильные требования;  
фичи в активной переработке;  
визуальные вещи, которые быстро меняются;  
проверки, где дешевле проверить руками.  

### Короткий ответ:

Автоматизация должна окупаться. Я бы автоматизировал стабильные, повторяемые и критичные сценарии, особенно на API и integration уровне.  

## 30. Как выбрать тесты для регрессии

Критерии:  

критичность функционала;  
зона изменений;  
история дефектов;  
интеграции;  
бизнес-риски;  
частота использования;  
покрытие автотестами;  
сложность модуля;  
влияние на деньги, безопасность, данные.  

### Пример ответа:

Я бы начал с анализа изменений: какие модули затронуты, какие зависимости есть, где раньше были дефекты. Потом выбрал бы smoke, критичные бизнес-сценарии и проверки вокруг изменённой области. Если есть автотесты, запустил бы релевантные наборы через CI.  

## 31. Тестирование новой фичи

### Алгоритм:

Изучить требования.  
Уточнить неоднозначности.  
Определить риски.  
Выделить позитивные и негативные сценарии.  
Применить техники тест-дизайна.  
Подготовить тестовые данные.  
Проверить API/БД/UI, если применимо.  
Выполнить функциональное тестирование.  
Завести дефекты.  
После исправления сделать ретест.  
Провести регрессию затронутых зон.  
Добавить автотесты, если сценарии стабильные и важные.  

## 32. Как тестировать без требований

Если требований нет или они неполные:  

поговорить с аналитиком/product owner;  
изучить макеты;  
посмотреть похожую функциональность;  
изучить API/логи/БД;  
использовать exploratory testing;  
составить вопросы;  
зафиксировать предположения;  
тестировать по здравому смыслу и бизнес-рискам.  

### Короткий ответ:

Если требований нет, я не просто начинаю хаотично кликать. Я собираю информацию: макеты, похожие фичи, API, бизнес-логику, задаю вопросы и фиксирую допущения. Потом тестирую по рискам.
