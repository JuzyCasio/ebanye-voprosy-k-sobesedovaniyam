## 81. Как отвечать на вопрос «Как бы вы тестировали…»

Универсальная структура ответа:  

Уточнил бы требования.  
Определил бы пользователей и роли.  
Выделил бы основные бизнес-сценарии.  
Проверил бы позитивные сценарии.  
Проверил бы негативные сценарии.  
Применил бы тест-дизайн.  
Проверил бы API/БД/UI, если применимо.  
Проверил бы интеграции.  
Проверил бы безопасность и права.  
Подумал бы о нефункциональных рисках.  
Добавил бы автотесты для стабильных критичных сценариев.  

Готовая фраза:  

Я бы начал с требований и рисков: кто пользователь, какая бизнес-цель, какие ограничения и какие интеграции затронуты. Потом выделил бы позитивные, негативные и граничные сценарии, проверил бы UI/API/БД в зависимости от архитектуры, отдельно посмотрел бы права доступа, обработку ошибок и регрессию затронутых зон.  

## 82. Как тестировать API endpoint на собеседовании

### Структура:

Method and URL.  
Auth.  
Headers.  
Request body.  
Query/path params.  
Status codes.  
Response schema.  
Business validation.  
Negative cases.  
DB side effects.  
Logs/events.  
Performance.  
Security.  
Idempotency.  

### Пример ответа:

Для endpoint я бы проверил успешный сценарий, валидацию входных данных, авторизацию, права доступа, статус-коды, схему ответа, побочные эффекты в БД, обработку ошибок зависимостей и поведение при повторных запросах.

### Структура:

Действия пользователя.

Ошибки.  
Навигация.

## 84. Как тестировать интеграцию

### Структура:

Какие системы участвуют.  
Кто инициатор.  
Формат данных.  
Контракт.  
Успешный сценарий.  
Ошибки зависимостей.  
Timeout.  
Retry.  
Дубли.  
Очереди.  
Логи.  
Monitoring.  
Idempotency.  
Data consistency.  

Готовая фраза:  

В интеграционном тестировании я бы проверил не только happy path, но и ошибки внешнего сервиса, таймауты, повторную отправку, дубли, несовместимость контракта и корректность итогового состояния данных.  

## 85. Что должен уметь Senior QA / SDET

Обычно ожидают:  

понимать архитектуру;  
тестировать не только UI, но и API/БД/интеграции;  
проектировать тестовую стратегию;  
выбирать, что автоматизировать;  
писать стабильные автотесты;  
работать с CI/CD;  
анализировать flaky-тесты;  
улучшать процессы;  
участвовать в code review;  
работать с логами;  
понимать Docker/Linux;  
разбираться в сетевых основах;  
менторить;  
объяснять риски бизнесу и команде.  

## 86. Хороший автотест

Характеристики:  

проверяет одну понятную вещь;  
независим от других тестов;  
сам готовит данные;  
сам чистит данные или использует изолированное окружение;  
имеет понятное название;  
имеет явные проверки;  
не содержит лишней логики;  
не использует sleep без необходимости;  
стабилен;  
быстро выполняется;  
даёт понятную ошибку при падении.  

### Плохой тест:

def test_1():  
    assert True  

Лучше:  

def test_user_can_create_order_with_valid_product() -> None:  
    ...  

## 87. Почему автотесты могут быть плохими

Причины:  

тестируют не то, что нужно;  
слишком много UI;  
нестабильные данные;  
нет изоляции;  
дублирование кода;  
сложные абстракции;  
плохие локаторы;  
нет отчётов;  
непонятные падения;  
долгий runtime;  
нет поддержки со стороны команды.  

## 88. Как ускорить автотесты

Способы:  

параллельный запуск;  
меньше UI, больше API/unit;  
оптимизация фикстур;  
переиспользование дорогих ресурсов;  
запуск только affected tests;  
разделение smoke/regression;  
мок внешних сервисов;  
подготовка данных через API/DB;  
убрать sleep;  
оптимизировать ожидания;  
запускать тесты по тегам;  
использовать test impact analysis.  

## 89. Как уменьшить количество багов

Не только тестировать в конце, а:  

участвовать в анализе требований;  
улучшать acceptance criteria;  
делать review тест-кейсов;  
внедрять code review;  
писать unit-тесты;  
использовать static analysis;  
улучшать CI;  
анализировать root cause;  
добавлять автотесты на найденные баги;  
улучшать тестовые данные;  
мониторить production.
