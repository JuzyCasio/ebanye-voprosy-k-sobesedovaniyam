## 19. Тестирование API

Что проверять в API  

### Основные группы проверок:

статус-код;  
тело ответа;  
схема ответа;  
заголовки;  
время ответа;  
авторизация;  
права доступа;  
валидация входных данных;  
обработка ошибок;  
идемпотентность;  
пагинация;  
сортировка;  
фильтрация;  
совместимость версий;  
логирование;  
интеграции;  
данные в БД.  
HTTP-методы  
GET  

Получение данных.  

Должен быть безопасным и идемпотентным.  

### Пример:

GET /users/123  
POST  

Создание ресурса или запуск операции.  

POST /users  
PUT  

Полное обновление ресурса.  

PUT /users/123  
PATCH  

### Частичное обновление ресурса.

PATCH /users/123  
DELETE  

Удаление ресурса.  

DELETE /users/123  
Идемпотентность  

Идемпотентная операция — повторный вызов даёт тот же результат с точки зрения состояния системы.  

Идемпотентные:  

GET;  
PUT;  
DELETE;  
HEAD;  
OPTIONS.  

Обычно неидемпотентный:  

POST.  

### Пример:

DELETE /user/1 один раз удалил пользователя.  
Повторный DELETE /user/1 не должен создать новое состояние, пользователь уже удалён.  
Статус-коды  
2xx  

Успешные ответы:  

200 OK;  
201 Created;  
202 Accepted;  
204 No Content.  
3xx  

Редиректы:  

301 Moved Permanently;  
302 Found;  
304 Not Modified.  
4xx  

Ошибка клиента:  

400 Bad Request;  
401 Unauthorized;  
403 Forbidden;  
404 Not Found;  
409 Conflict;  
422 Unprocessable Entity;  
429 Too Many Requests.  
5xx  

Ошибка сервера:  

500 Internal Server Error;  
502 Bad Gateway;  
503 Service Unavailable;  
504 Gateway Timeout.  
401 vs 403  
401 Unauthorized  

Пользователь не аутентифицирован.  

### Пример:

Нет токена или токен невалиден.  

403 Forbidden  

Пользователь аутентифицирован, но прав недостаточно.  

### Пример:

Пользователь залогинен, но пытается открыть админскую страницу.  

### Короткий ответ:

401 — система не знает, кто ты. 403 — знает, кто ты, но тебе нельзя.  

400 vs 422  
400 Bad Request  

Некорректный запрос в целом.  

Например:  

битый JSON;  
неверный формат запроса;  
отсутствует обязательная структура.  
422 Unprocessable Entity  

Запрос синтаксически корректный, но бизнес-валидация не прошла.  

Например:  

email неправильного формата;  
возраст меньше допустимого;  
пароль слишком короткий.  
404 vs 409  
404 Not Found  

Ресурс не найден.  

409 Conflict  

Конфликт состояния.  

### Примеры:

пользователь с таким email уже существует;  
заказ уже оплачен;  
нельзя отменить доставленный заказ.  
Проверки POST /users  

Допустим, есть API:  

POST /users  

Тело:  

{  
  "username": "alex",  
  "password": "Password123"  
}  

Ожидаемый успешный ответ:  

{  
  "id": 1,  
  "username": "alex"  
}  

### Проверки:

Позитивные  
валидный username/password → 201;  
в ответе есть id;  
username совпадает;  
пароль не возвращается;  
пользователь появился в БД;  
можно залогиниться созданным пользователем.  
Негативные  
пустой username;  
пустой password;  
username уже существует;  
короткий password;  
password без цифр;  
password без заглавных букв;  
слишком длинный username;  
спецсимволы;  
пробелы;  
отсутствует body;  
битый JSON;  
неверный Content-Type.  
Авторизация  
если endpoint публичный — токен не нужен;  
если endpoint закрытый — без токена 401;  
с токеном без прав 403.  
Безопасность  
пароль не возвращается;  
пароль не логируется;  
SQL/XSS payload не ломает API;  
rate limit на массовые регистрации.  

## 20. REST API: что важно знать

REST — архитектурный стиль для построения API.  

### Основные идеи:

ресурсы;  
URI;  
HTTP-методы;  
stateless;  
стандартные статус-коды;  
представления ресурсов в JSON/XML;  
кэширование, где применимо.  

### Пример хорошего REST:

GET /users  
GET /users/123  
POST /users  
PATCH /users/123  
DELETE /users/123  

### Плохой стиль:

GET /getUser  
POST /deleteUser  
POST /updateUserName  

## 21. Контрактное тестирование

Контрактное тестирование проверяет, что сервисы правильно взаимодействуют друг с другом по согласованному контракту.  

Например:  

сервис A ожидает от сервиса B поле user_id;  
сервис B изменил поле на id;  
контрактный тест должен поймать поломку.  

Полезно в микросервисах.  

Инструменты:  

Pact;  
Spring Cloud Contract;  
Schemathesis;  
OpenAPI schema validation.  

### Короткий ответ:

Контрактные тесты помогают проверить совместимость сервисов без необходимости поднимать всю систему целиком.
