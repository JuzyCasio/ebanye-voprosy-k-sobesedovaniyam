## 22. Моки, стабы, фейки

Dummy  

Объект-заглушка, который передаётся, но не используется.  

Stub  

Возвращает заранее подготовленный ответ.  

### Пример:

Внешний сервис всегда возвращает {status: "ok"}.  

Mock  

Проверяет, что его вызвали нужным образом.  

### Пример:

Проверяем, что метод send_email() был вызван один раз с нужным email.  

Fake  

Упрощённая рабочая реализация.  

### Пример:

In-memory база вместо настоящей.  

Spy  

Запоминает вызовы, но может при этом выполнять реальную логику.  

### Короткий ответ:

Stub нужен, чтобы подменить ответ зависимости. Mock — чтобы проверить взаимодействие с зависимостью.  

## 23. Тестирование БД

### Что проверять:

данные создались;  
данные обновились;  
данные удалились;  
связи корректные;  
constraints работают;  
уникальность;  
nullable/non-nullable;  
foreign keys;  
транзакции;  
rollback;  
индексы;  
миграции;  
корректность типов;  
округления;  
даты и timezone.  
Типовые SQL-проверки  
Проверить, что пользователь создан  
SELECT id, username, email  
FROM users  
WHERE email = 'test@example.com';  
Проверить количество записей  
SELECT COUNT(*)  
FROM orders  
WHERE user_id = 123;  
Проверить уникальность  
SELECT email, COUNT(*)  
FROM users  
GROUP BY email  
HAVING COUNT(*) > 1;  
Проверить связи  
SELECT o.id, u.email  
FROM orders o  
JOIN users u ON o.user_id = u.id  
WHERE o.id = 1001;  
Что такое транзакция  

Транзакция — набор операций, который должен выполниться полностью или не выполниться вообще.  

ACID:  

Atomicity — атомарность;  
Consistency — согласованность;  
Isolation — изоляция;  
Durability — долговечность.  

### Пример:

При переводе денег нужно списать сумму с одного счёта и зачислить на другой. Нельзя выполнить только одну из операций.  

## 24. Тестирование микросервисов

### Что важно проверять:

API каждого сервиса;  
контракты между сервисами;  
обработку недоступности зависимостей;  
таймауты;  
ретраи;  
circuit breaker;  
очереди;  
идемпотентность;  
eventual consistency;  
логи;  
трассировку;  
метрики;  
права доступа;  
версионирование API.  
Типовые проблемы в микросервисах  
сервис недоступен;  
сервис отвечает долго;  
изменился контракт;  
сообщение потерялось;  
сообщение обработалось два раза;  
данные в сервисах рассинхронизировались;  
retry создал дубликаты;  
разные версии сервисов несовместимы.  

## 25. Тестирование брокеров сообщений

Например:  

Kafka;  
RabbitMQ;  
NATS;  
Redis Streams.  

### Что проверять:

сообщение публикуется;  
сообщение читается consumer’ом;  
формат сообщения корректный;  
обязательные поля есть;  
порядок сообщений;  
повторная обработка;  
дубликаты;  
dead letter queue;  
retry;  
offset/ack;  
поведение при падении consumer’а;  
поведение при недоступности брокера;  
идемпотентность обработки.  

### Короткий ответ:

При тестировании брокеров важно проверять не только сам факт доставки, но и обработку дублей, повторов, ошибок, ack/nack, DLQ и устойчивость consumer’ов.  

## 26. UI-тестирование

### Что проверять в UI:

элементы отображаются;  
кнопки кликабельны;  
формы работают;  
ошибки отображаются;  
данные корректны;  
навигация работает;  
адаптивность;  
кроссбраузерность;  
accessibility;  
локализация;  
состояние после refresh;  
deep links;  
работа с cookies/localStorage/sessionStorage.  
UI-автотесты  

### Плюсы:

проверяют поведение как пользователь;  
хорошо подходят для критичных сценариев;  
находят интеграционные проблемы.  

### Минусы:

медленные;  
хрупкие;  
зависят от окружения;  
требуют стабильных локаторов;  
сложны в поддержке.  

### Короткий ответ:

UI-тесты нужны, но ими не стоит покрывать всё подряд. Критичная логика должна проверяться ниже: unit, integration, API. UI лучше оставить для ключевых пользовательских сценариев.  

### Хорошие локаторы

Лучше использовать:  

data-testid;  
data-qa;  
уникальные id;  
role-based selectors;  
text, если он стабилен.  

Хуже использовать:  

длинные XPath;  
CSS, завязанные на структуру;  
auto-generated классы;  
индексы элементов.  

### Плохой локатор:

/html/body/div[2]/div[3]/button[1]  

### Хороший локатор:

[data-testid="submit-button"]
