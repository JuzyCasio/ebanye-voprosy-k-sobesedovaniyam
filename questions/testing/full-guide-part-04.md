Темы 7.

## 7. Тест-дизайн

Тест-дизайн — это проектирование тестов так, чтобы небольшим количеством проверок покрыть максимум рисков.  

Классы эквивалентности  

Используются, когда много данных можно разбить на группы, внутри которых система должна вести себя одинаково.  

### Пример:

Поле возраста принимает значения от 18 до 65.  

Классы:  

меньше 18 — невалидно;  
18–65 — валидно;  
больше 65 — невалидно;  
пустое значение — невалидно;  
нечисловое значение — невалидно.  

Для каждого класса обычно берём 1–2 значения.  

Граничные значения  

### Часто баги возникают на границах.

Если допустимый диапазон 18–65, проверяем:  

17;  
18;  
19;  
64;  
65;  

### Короткий ответ:

Классы эквивалентности помогают сократить количество тестов, а граничные значения позволяют найти баги на переходах между валидными и невалидными зонами.  

Таблица принятия решений  

Используется, когда результат зависит от комбинации условий.  

### Пример: скидка в интернет-магазине.

Условия:  

пользователь авторизован;  
есть промокод;  
сумма заказа больше 5000;  
пользователь VIP.  

Результаты:  

скидка 0%;  
скидка 5%;  
скидка 10%;  
ошибка промокода.  

Таблицы решений хорошо подходят для:  

бизнес-правил;  
расчётов;  
прав доступа;  
тарифов;  
скидок;  
условий доставки.  
Диаграмма состояний  

Используется, когда объект может находиться в разных состояниях.  

### Пример заказа:

Created;  
Paid;  
Cancelled;  
Shipped;  
Delivered;  
Refunded.  

### Что тестировать:

допустимые переходы;  
запрещённые переходы;  
повторные действия;  
переходы после ошибок;  
права пользователей на переходы.  

### Пример:

Created → Paid — можно;  
Paid → Shipped — можно;  
Delivered → Cancelled — нельзя;  
Cancelled → Paid — нельзя.  
Pairwise Testing  

Используется, когда много параметров и невозможно проверить все комбинации.  

### Пример:

браузер: Chrome, Firefox, Safari;  
ОС: Windows, macOS, Linux;  
язык: RU, EN;  
роль: admin, user.  

Полный перебор: 3 × 3 × 2 × 2 = 36 проверок.  

Pairwise позволяет покрыть пары параметров меньшим количеством тестов.  

Use Case Testing  

### Проверка пользовательских сценариев.

### Пример:

Пользователь оформляет заказ с доставкой.  

Шаги:  

Открыть каталог.  
Добавить товар.  
Перейти в корзину.  
Указать адрес.  
Выбрать оплату.  
Подтвердить заказ.  
Получить номер заказа.  
Error Guessing  

### Проверка на основе опыта тестировщика.

### Примеры:

пустые поля;  
пробелы;  
спецсимволы;  
длинные строки;  
дубли;  
неверные форматы;  
повторная отправка формы;  
потеря сети;  
истёкшая сессия;  
двойной клик;  
обновление страницы;  
конкурентные запросы.  
Checklist-based Testing  

### Проверка по чек-листу.

### Плюсы:

быстрее тест-кейсов;  
удобно для регрессии;  
гибко;  
меньше поддержки.  

### Минусы:

меньше детализации;  
зависит от опыта тестировщика.
