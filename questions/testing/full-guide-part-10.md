## 33. Риск-ориентированное тестирование

Риск = вероятность проблемы × влияние проблемы.  

Высокий риск:  

влияет на деньги;  
влияет на безопасность;  
влияет на данные пользователей;  
часто используется;  
сложная логика;  
много интеграций;  
недавно менялось;  
раньше часто ломалось.  

### Пример:

В банковском приложении платежи, авторизация и переводы имеют больший приоритет, чем изменение аватарки.  

## 34. Тестовые данные

### Виды тестовых данных:

валидные;  
невалидные;  
граничные;  
пустые;  
минимальные;  
максимальные;  
реальные;  
синтетические;  
обезличенные;  
данные для ролей;  
данные для ошибок;  
данные для интеграций.  

### Что важно:

данные должны быть воспроизводимыми;  
тесты не должны зависеть от случайного состояния;  
данные лучше создавать через API/fixtures/factory;  
после тестов нужно чистить данные или использовать изоляцию.  

## 35. Изоляция тестов

### Хороший автотест должен быть:

независимым;  
воспроизводимым;  
стабильным;  
понятным;  
быстрым;  
самодостаточным.  

### Плохая практика:

тест зависит от результата предыдущего теста;  
тест использует общую учётку, которую могут менять другие тесты;  
тест требует ручной подготовки данных;  
тест падает из-за порядка запуска.  

Способы изоляции:  

создавать данные перед тестом;  
удалять данные после теста;  
использовать уникальные данные;  
использовать транзакции и rollback;  
использовать отдельные схемы БД;  
использовать Docker-контейнеры;  
использовать mocks/stubs;  
запускать тесты в независимом окружении.  

## 36. Flaky tests

Flaky test — тест, который иногда проходит, иногда падает без изменения кода.  

Причины:  

нестабильное окружение;  
race condition;  
ожидания через sleep;  
зависимость от времени;  
зависимость от порядка тестов;  
общие тестовые данные;  
нестабильные локаторы;  
сеть;  
внешние сервисы;  
асинхронная обработка;  
параллельный запуск.  

### Что делать:

заменить sleep на явные ожидания;  
изолировать данные;  
стабилизировать окружение;  
добавить retry только как временную меру;  
логировать состояние;  
анализировать причину;  
не игнорировать flaky-тесты.  

### Короткий ответ:

Flaky-тесты опасны, потому что подрывают доверие к автотестам. Их нужно анализировать как отдельный технический долг, а не просто перезапускать.  

## 37. Тестирование асинхронных процессов

### Примеры:

отправка email;  
обработка сообщения из брокера;  
генерация отчёта;  
обновление статуса заказа;  
фоновые задачи.  

### Что проверять:

задача запустилась;  
статус изменился;  
результат появился;  
ошибки обработались;  
повторная обработка;  
таймауты;  
retry;  
идемпотентность;  
логи;  
события в брокере;  
состояние в БД.  

### Подход:

не использовать слепой sleep;  
использовать polling с таймаутом;  
проверять конечное состояние;  
по возможности читать события/логи/БД.  

### Пример идеи:

import time  
from collections.abc import Callable  

def wait_until(  
    condition: Callable[[], bool],  
    timeout: float = 10.0,  
    interval: float = 0.5,  
) -> None:  
    started_at = time.time()  

    while time.time() - started_at < timeout:  
        if condition():  
            return  
        time.sleep(interval)  

    raise TimeoutError("Condition was not met")  

## 38. CI/CD и тестирование

Что такое CI  

Continuous Integration — регулярная интеграция изменений в общий репозиторий с автоматическим запуском проверок.  

### Примеры:

линтеры;  
unit-тесты;  
API-тесты;  
сборка Docker-образа;  
статический анализ;  
smoke.  
Что такое CD  

Continuous Delivery/Deployment — автоматизированная доставка изменений до окружений.  

### Что запускать в pipeline

Обычно:  

Lint.  
Type checking.  
Unit tests.  
Build.  
Integration tests.  
API tests.  
Smoke tests.  
Regression по расписанию или перед релизом.  
Report.  
Quality Gate  

Quality Gate — набор условий, без выполнения которых изменение нельзя продвигать дальше.  

### Примеры:

все critical tests passed;  
нет blocker defects;  
coverage не ниже порога;  
линтер без ошибок;  
security scan без critical;  
сборка успешна.  

### Короткий ответ:

Quality Gate — это автоматический контроль качества в pipeline. Он не даёт пропустить изменение дальше, если не выполнены обязательные проверки.
